# Наблюдение на Supreme Bot — трите аларми

**Създадено при одита на 07.08.2026.** Наблюдателят препоръча три аларми; дотук
имахме endpoint-и, но никой не ги гледаше. Endpoint без сонда е мъртъв код.

Алармите са **по СИМПТОМ, не по причина** — това, което клиентът усеща, а не
това, което вътрешно се е счупило. Причина без симптом вдига шум; симптом без
причина се разследва, но поне се знае, че има проблем.

---

## 1. Основният път е мъртъв

**Симптом:** клиентът отваря таблото и не работи нищо.

| | |
|---|---|
| Сонда | HTTP GET `https://supremebot.carbonstealth.eu/api/status/probe` |
| Здраво | HTTP **200** |
| Аларма | два поредни неуспеха (или 503) на интервал 60s |
| Реакция | `journalctl -u docker -n 200`, после `docker compose ps` в релийза |

Пробата връща **празно тяло, само код**: 200 = база + Redis + Discord gateway са
живи; 503 = поне един е паднал. Подробностите са на `/api/status` (той нарочно
винаги връща 200 — страницата за състояние трябва да ПОКАЖЕ повредата, не да
падне в грешка).

> Не насочвай сондата към `/api/status` — тя връща 200 и при `degraded`, значи
> алармата никога няма да се вдигне.

## 2. Платена работа спира тихо

**Симптом:** насрочените съобщения не тръгват, анкетите не се затварят,
неактивните тикети не се затварят — платени функции, които просто мълчат.

Този клас вече ни изгоря веднъж: три cron задачи споделяха ключ за заключване и
две от тях **никога** не се изпълняваха. Открихме го при одит, не от аларма.

| | |
|---|---|
| Сонда | keyword върху `https://supremebot.carbonstealth.eu/api/status` |
| Здраво | тялото съдържа `"status":"operational"` |
| Аларма | липса на думата, или последно успешно изпълнение на задача > 26 часа |

Най-евтиният сигнал без нова инфраструктура е **пулсът на самия планировчик**:
от 09.08.2026 ВСЯКА задача (вкл. минутните, дроселирани до 1 запис/час, и
осиновените ГДПР ретенция + дунинг) пише `JOB_OK_<ИМЕ>` в `audit_logs`. Заявка
за ръчна проверка:

```sql
SELECT action, max("createdAt") AS последно
FROM audit_logs
WHERE action LIKE 'JOB_OK_%'
GROUP BY action;
```

Всяко „последно“ по-старо от денонощие значи спряла задача (за минутните —
по-старо от 2 часа). **НЕ следи `PREMIUM_GRACE_EXPIRED`** — това е маркер за
СВЪРШЕНА РАБОТА, не за изпълнен ран: пише се само когато е имало какво да се
свали, тоест тих месец вдига фалшива тревога всеки ден И е сляп за реално
спрял дунинг. Дунингът вече има собствен ран-пулс: `JOB_OK_DUNNING`. От 07.08.2026 всеки
провал на задача минава през `jobFail` → Sentry с таг `job:<име>`, значи
алармата може да е и **Sentry правило по този таг**.

## 3. Бранд ботовете мълчат

**Симптом:** клиент на White-label казва „ботът ми не отговаря“.

| | |
|---|---|
| Сонда | keyword върху `http://127.0.0.1:3001/health` (през SSH тунел или вътрешно) |
| Здраво | `"gateway":"connected"` **и** `"down":0` |
| Аларма | `"down"` > 0 за повече от 15 минути |

**Важно защо е отделна от рестарта:** паднал бранд бот е чужд проблем (изтекъл
или сменен токен на клиента) и **не бива** да рестартира нашия бот — затова
броят паднали е в ТЯЛОТО на `/health`, а не в кода му. Docker гледа кода;
човекът гледа тялото.

## Настройка с Uptime Kuma (препоръчано)

Vpsdash вече върви на машината; Kuma е най-лекото допълнение.

```bash
docker run -d --restart=always -p 127.0.0.1:3010:3001 \
  -v uptime-kuma:/app/data --name uptime-kuma louislam/uptime-kuma:1
```

После в интерфейса, по един монитор на аларма:

| Монитор | Тип | URL | Условие |
|---|---|---|---|
| Supreme · основен път | HTTP(s) | `…/api/status/probe` | приема само 200, интервал 60s, повторения 2 |
| Supreme · компоненти | Keyword | `…/api/status` | ключова дума `"status":"operational"` |
| Supreme · бранд ботове | Keyword | `http://127.0.0.1:3001/health` | ключова дума `"down":0` |

Известяване: Discord webhook към канал, който наистина четеш. Аларма в канал,
който никой не гледа, е същото като липсваща.

## Проверка, че алармите РАБОТЯТ

Аларма, която никога не се е вдигала, е непроверена хипотеза. Веднъж след
настройката:

```bash
docker compose stop redis     # пробата трябва да почервенее до 2 минути
docker compose start redis    # и да позеленее сама
```

Ако не почервенее, сондата гледа грешното нещо — поправи я СЕГА, а не в нощта
на първия инцидент.
