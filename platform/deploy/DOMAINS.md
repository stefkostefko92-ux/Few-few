# Домейни и публикуване — от създаване до жив сайт

Пълен, професионален наръчник за жизнения цикъл на сайт в платформата: от
създаване на страници до пускане на **наш поддомейн** (`*.carbonstealth.site`)
или **собствен домейн на клиента** (`example.com`), с автоматичен TLS и правилни
пренасочвания. Технически насочен (за оператора и за VPS-аджията).

---

## 0. Терминология и архитектура

| Понятие | Стойност |
| --- | --- |
| Панел / маркетинг хост | `platform.carbonstealth.eu` (и `localhost` в разработка) |
| Апекс за наши поддомейни | `carbonstealth.site` (env `PLATFORM_APEX`) |
| Наш поддомейн на клиент | `<subdomain>.carbonstealth.site` |
| Собствен домейн на клиент | напр. `example.com`, `www.example.com` |
| Вътрешен адрес (винаги наличен) | `platform.carbonstealth.eu/site/<slug>` |

**Как заявката стига до правилния сайт** (`src/middleware.ts`):

1. Идва HTTP заявка с `Host:` заглавие.
2. Ако хостът е **платформен** (`isPlatformHost`) → нормално рутиране (панел, `/site/*`, API).
3. Иначе (наш поддомейн или собствен домейн) middleware **пренаписва** пътя към
   `/hosted{path}`, като запазва оригиналния `Host`.
4. `src/app/hosted/[[...path]]/page.tsx` чете `Host`, резолвира сайта
   (`siteByHost` → по `subdomain` или по потвърден `customDomain`) и рендира
   публичния изглед (`PublicSiteView`) — същия като на `/site/<slug>`.

Резолюцията е чиста и тествана: `subdomainOf`, `isValidSubdomain`, `isValidDomain`
(`src/lib/domains.ts`, unit тестове в `__tests__/domains.test.ts`).

## 1. Създаване и публикуване на сайта (в панела)

1. **Свържи сайт** → създава `Site` (уникален `slug`).
2. **Конструктор на страници** → добави блокове (или AI/шаблон), качи снимки,
   задай меню/SEO per страница (`showInNav`, `navOrder`, `seoTitle`, `seoDescription`).
3. **Настройки на сайта** (`/dashboard/sites/<slug>/settings`):
   - Външен вид: основен цвят, шрифт, лого, favicon.
   - Меню/футър: импресум (контакти) и връзка към поверителност.
4. **Публикувай** всяка страница (BG и по избор EN).
5. В **Домейни и публикуване** включи ключа **„Сайтът е публикуван"**
   (`Site.published = true`) — това е условието сайтът да се обслужва на
   домейн/поддомейн (вътрешният `/site/<slug>` работи и без него).

> **Воден знак:** безплатните сайтове (`Site.premium = false`) показват дискретен
> знак „Създадено с Carbon Stealth" във футъра. Премахва се при `premium = true`
> (за момента се включва от собственик; по-нататък — през билинг).

## 2. Вариант А — наш поддомейн (`<sub>.carbonstealth.site`)

Най-бързият път, без намеса на клиента в DNS.

### 2.1 Еднократна инфраструктура (веднъж за платформата)
- Притежавай домейна `carbonstealth.site`.
- Насочи **wildcard** запис към сървъра:
  - `*.carbonstealth.site  A  <IP-на-сървъра>` (и `AAAA` при IPv6).
- Caddy издава **wildcard TLS** сертификат чрез DNS-01 предизвикателство
  (нужен е DNS плъгин с API ключ на регистратора) — виж §4.2. Алтернатива:
  On-Demand TLS за всеки поддомейн (§4.1).

### 2.2 За всеки клиент
1. В **Настройки → Домейни** въведи поддомейн (напр. `myrestaurant`) → запази.
   - Валидира се като DNS етикет, проверява се за заетост и запазени имена
     (`www`, `api`, …). Записва се в `Site.subdomain`.
2. Готово — сайтът е на `https://myrestaurant.carbonstealth.site` (при `published`).

Няма нужда от верификация — ние контролираме DNS на апекса.

## 3. Вариант Б — собствен домейн на клиента (`example.com`)

### 3.1 Стъпки в панела
1. **Настройки → Домейни → Собствен домейн** → въведи `example.com` → запази.
   - Генерира се таен токен и се показват DNS инструкции. `domainVerified = false`.

### 3.2 DNS записи, които клиентът добавя при своя регистратор

**а) Доказване на собствеността (TXT):**

```
Тип: TXT
Име: @            (или _carbonstealth)
Стойност: carbonstealth-verify=<токенът от панела>
```

**б) Насочване на трафика към нас:**

- **Поддомейн** (напр. `www.example.com`):
  ```
  Тип: CNAME
  Име: www
  Стойност: <sub>.carbonstealth.site      (или общ таргет, напр. sites.carbonstealth.site)
  ```
- **Основен домейн / apex** (`example.com`) — CNAME на apex обикновено не е
  позволен, затова:
  ```
  Тип: A
  Име: @
  Стойност: <IP-на-сървъра>
  ```
  (или ALIAS/ANAME, ако регистраторът го поддържа).

Препоръка: пренасочи apex → `www` (или обратно) на ниво DNS/сървър, за да има
един каноничен адрес.

### 3.3 Потвърждение и активиране
1. Клиентът натиска **„Провери домейна"** → сървърът прави DNS TXT справка
   (`verifyDomainAction`, `node:dns`), сравнява с очаквания токен.
2. При успех `domainVerified = true` → middleware вече обслужва `example.com`.
3. TLS сертификатът се издава **автоматично при първото HTTPS посещение** през
   Caddy On-Demand TLS (§4.1) — без ръчна намеса.

## 4. TLS (HTTPS) на сървъра — Caddy

Caddy стои отпред (reverse proxy) и проксира към Next (`127.0.0.1:3000`).

### 4.1 On-Demand TLS + „ask" endpoint (за собствени домейни и поддомейни)

Caddy пита нашия сървър преди да издаде сертификат за произволен домейн, за да не
издава за чужди/непринадлежащи хостове. Ендпойнтът е `GET /api/tls-check?domain=`:
връща **200** само за домейни, които наистина обслужваме (наш поддомейн на
публикуван сайт, или потвърден собствен домейн), иначе **403**.

`Caddyfile` (примерно):

```caddy
{
    # Позволи сертификати само за домейни, одобрени от платформата
    on_demand_tls {
        ask https://platform.carbonstealth.eu/api/tls-check
        interval 2m
        burst 5
    }
    email admin@carbonstealth.eu
}

# Панелът/маркетингът (обикновен, известен домейн)
platform.carbonstealth.eu {
    reverse_proxy 127.0.0.1:3000
}

# Всички клиентски сайтове: наши поддомейни + собствени домейни (on-demand)
https:// {
    tls {
        on_demand
    }
    reverse_proxy 127.0.0.1:3000
    header X-Forwarded-Proto https
}
```

> Важно: `/api/tls-check` пази срещу издаване на сертификати за чужди домейни
> (subdomain enumeration / abuse). Дръж `interval`/`burst` разумни.

### 4.2 Алтернатива за наши поддомейни: wildcard сертификат (DNS-01)

Ако предпочиташ един wildcard вместо on-demand за поддомейните:

```caddy
*.carbonstealth.site {
    tls {
        dns <провайдър> {env.DNS_API_TOKEN}   # напр. cloudflare
    }
    reverse_proxy 127.0.0.1:3000
    header X-Forwarded-Proto https
}
```

Wildcard TLS изисква DNS-01, значи Caddy build с плъгин за твоя DNS доставчик.

## 5. Пренасочвания (redirects) — препоръки

- **apex ↔ www:** избери каноничен вариант и пренасочи другия (301) на ниво
  Caddy, за да няма дублирано съдържание/SEO разсейване.
- **HTTP → HTTPS:** Caddy прави автоматично.
- **Вътрешен `/site/<slug>` при активен домейн:** остава достъпен, но за SEO
  каноничният адрес на публичните страници сочи към текущия хост
  (`generateMetadata` в `hosted/[[...path]]` използва реалния `Host`), а
  `hreflang`/`canonical` са per език.

Пример за apex→www в Caddy:

```caddy
example.com {
    redir https://www.example.com{uri} permanent
}
```

## 6. Чеклист „преди да дам адреса на клиента"

- [ ] Сайтът има публикувана начална страница (BG), меню и импресум.
- [ ] `Site.published = true`.
- [ ] Наш поддомейн зададен **или** собствен домейн потвърден (`domainVerified`).
- [ ] `*.carbonstealth.site` (wildcard) сочи към сървъра (за поддомейни).
- [ ] Caddy on-demand TLS + `ask` към `/api/tls-check` работи (виж лог при първо
      посещение — трябва да издаде сертификат).
- [ ] Отваряне на адреса → 200, коректно лого/цвят/меню; воден знак само ако не е премиум.
- [ ] (по избор) apex→www redirect настроен.

## 7. Отстраняване на проблеми

| Симптом | Причина / решение |
| --- | --- |
| Домейнът не се потвърждава | TXT още не се е разпространил (до час); провери с `dig TXT example.com` |
| „404" на собствен домейн | `domainVerified=false` или `published=false`; DNS не сочи към нас |
| Няма HTTPS / грешка в сертификата | `/api/tls-check` върна 403 (домейнът не е одобрен) или apex A запис липсва |
| Показва празна EN версия | Страницата няма EN блокове — резервът е BG; EN се рекламира само при налично съдържание |
| Водният знак не изчезва | `Site.premium` все още е `false` |
