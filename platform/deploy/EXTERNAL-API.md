# Договор с външен свързан сайт (CMS прокси)

Платформата може да наблюдава и управлява **външни** (несъздадени тук) сайтове —
да чете техните здравни проверки, да издърпва (и вече да **записва**) съдържание,
и да задейства деплой. Този документ описва HTTP договора, който външният сайт
трябва да реализира, за да работят тези функции.

Всичко живее в `src/lib/sites.ts`. За всеки сайт в платформата се задават:

| Поле в сайта   | Значение                                                              |
| -------------- | --------------------------------------------------------------------- |
| `url`          | Публичен адрес — проверява се за здраве (GET, без ключ).               |
| `apiBaseUrl`   | Базов адрес на API-то на сайта (за съдържание и деплой).              |
| `apiKeyEnc`    | API ключ на сайта — **криптиран при нас** (AES-256-GCM), пращан като `Bearer`. |
| `deployHookUrl`| По избор: собствен адрес за деплой (иначе `apiBaseUrl/api/platform/deploy`). |

Ключът се пази криптиран в базата и се дешифрира само в момента на заявката. Той
пътува единствено през HTTPS в `Authorization: Bearer <ключ>`. Външният сайт
трябва да го проверява при всяка заявка към `/api/platform/*` и да отхвърля с
`401`, ако липсва или е грешен.

---

## 1. Здраве — `GET <url>`

Обикновена публична заявка (без ключ). Платформата смята сайта за:

- **UP** при `2xx/3xx` под 3 s,
- **DEGRADED** при отговор над 3 s,
- **DOWN** при `4xx/5xx`, таймаут (10 s) или мрежова грешка.

Нищо специално не се изисква — стига страницата да връща статус код.

## 2. Съдържание (четене) — `GET <apiBaseUrl>/api/platform/content`

Заглавие: `Authorization: Bearer <ключ>`. Отговор `200` с JSON:

```json
{
  "items": [
    { "id": "42", "kind": "post", "title": "Заглавие", "status": "published", "url": "https://…" }
  ]
}
```

- `id` — **задължителен**, стабилен идентификатор в самия сайт (пази се като `externalId`).
- `kind` — тип (`post` | `listing` | `page` | …); по подразбиране `item`.
- `title`, `status` (`published` | `draft` | …), `url` — по избор.

Платформата кешира резултата локално (`ContentItem`, само огледало) при
„Синхронизирай“. Това е **само четене** — нищо не се презаписва в сайта тук.

## 3. Съдържание (запис) — `PUT <apiBaseUrl>/api/platform/content/<id>`

**Ново.** Позволява редакция от таблото на един елемент по неговия `id` (същия,
върнат от точка 2). Заглавия:

```
Authorization: Bearer <ключ>
Content-Type: application/json
```

Тяло — само подадените полета (частично обновяване):

```json
{ "title": "Нов текст", "status": "published" }
```

- `title` — по избор, `1..300` знака.
- `status` — по избор, само `"published"` или `"draft"` (платформата валидира
  преди да прати; не изпраща други стойности).

Сайтът **сам записва** промяната и връща `2xx` при успех (тялото се игнорира).
При грешка връща `4xx/5xx` — платформата НЕ обновява локалното огледало (то се
пипа само след потвърждение). Отговорност на сайта е авторизацията и валидацията
от негова страна — платформеният `Bearer` ключ е доверие на ниво сайт, не на
ниво отделен потребител.

Идемпотентност: повторен `PUT` със същото тяло трябва да е безопасен (просто
записва същите стойности).

## 4. Деплой — `POST <deployHookUrl | apiBaseUrl/api/platform/deploy>`

Заглавие: `Authorization: Bearer <ключ>`. Празно тяло. `2xx` = деплоят е приет
(поставен на опашка). Платформата записва `Deployment` със статус според отговора.

---

## Сигурност (обобщено)

- Ключът е **криптиран при нас**; никога не се логва и не се връща в UI.
- Всички извиквания са с **10 s таймаут** и се броят като неуспех при изтичане.
- Записът (точка 3) е ограничен до роля **MANAGER** върху сайта и се вписва в
  одита (`AuditLog`, действие `UPDATE`).
- Външният сайт трябва да третира `Bearer` ключа като таен и да го върти при
  съмнение за изтичане (смяна на ключа става от настройките на сайта в платформата).
