# CLAUDE.md — vpsdash

**Carbon Stealth VPS Dashboard** — пълен контролен панел за VPS сървърите с графичен
интерфейс. Управлява **всичко** от един екран: метрики на живо, systemd услуги,
Docker, процеси, journal логове, деплой (по канона на autodeploy.sh), apt ъпдейти,
сигурност (ufw/fail2ban/TLS/SSH/портове), бекъпи, крон/таймери, файлов браузър,
уеб терминал, агентския флот и одиторски дневник. Управлява **и двата VPS-а** от
един панел през federation (peer proxy).

## Стек
- **Backend:** Node ≥20, `node:http` — **нула runtime зависимости** (като ospedali).
  Само `devDependencies` няма — тества се с вградения `node --test`.
- **Frontend:** vanilla ES modules + `<canvas>` за графиките — нула build стъпка,
  нула външни ресурси (CSP-friendly, `noindex`).
- **Данни:** без база — конфиг в `/etc/vps-dashboard/config.json` (mode 600), state
  (одит журнал) в `/var/lib/vps-dashboard`.

## Команди (quality gate)
```bash
cd vpsdash
npm run lint     # node --check на всеки .js/.mjs (scripts/syntax-check.mjs)
npm test         # node --test test/*.test.js
npm run sweep    # браузърна обиколка на 37-те секции (иска Playwright)
npm run degraded # машина БЕЗ инструменти: гърми ли, лъже ли с „нула проблема"
npm start        # прод (иска /etc/vps-dashboard/config.json)
npm run dev      # CSD_DEV=1 — ефимерен конфиг + еднократна парола в конзолата
```
Гейтът е `npm run lint && npm test`. Пусни го преди commit/PR.

**Пусни и `npm run sweep`, когато си пипал `public/`.** `node --check` вижда само
синтаксис, `node --test` не рендва интерфейс — променлива в грешен обхват минава
и двете и чупи ЦЯЛА секция. Реален случай: `const broken` беше деклариран вътре в
`else`, а се ползваше след него → „Ъпдейти" отговаряше само `Грешка: broken is not
defined`, при 380 зелени теста. Обиколката влиза във всяка секция с истински
Chromium и пада при `Грешка:` в `#view`, празен изглед, JS изключение, 5xx или
непреведен низ. Чака СКЕЛЕТЪТ да си отиде, не фиксирано време (apt отнема ~2 s).
Пропуска се тихо (изход 0), ако Playwright липсва — не е зависимост на продукта.

## Конвенции (важни)
- **Нула зависимости.** Не добавяй npm пакети — всичко е stdlib. Ако нещо иска пакет,
  напиши го на ръка или го изостави.
- **Fail-closed сигурност.** Всеки API маршрут минава през `guard()` (сесия/Bearer),
  мутациите — и през CSRF (custom header + Origin). Системните команди вървят през
  `execFile` с масив аргументи (**без shell**); shell има само `/api/terminal/run`,
  изрично и **одитирано**. Имената на unit-и/контейнери минават през allowlist regex.
- **Тайните живеят само на сървъра** (config.json mode 600). Никога в репото/архива.
  Одитът никога не записва пароли/токени. Панелът слуша само на `127.0.0.1` — публично
  само зад Nginx + TLS (+ по избор Basic-auth).
- **Деплой = канонът на репото.** Панелът не преоткрива деплой: пуска `deploy/autodeploy.sh`
  като фонова задача с жив изход. Продуктовите health URL-и в config съвпадат с него.
- **Български UI.** Всички низове на потребителя са на български („…“ кавички).
- **Federation.** Един и същ панел на всеки VPS. `peers[]` в config сочат другите; заявки
  към `/api/nodes/<id>/*` се проксират с `peerToken` (Bearer). Другият край приема
  Bearer == своя `peerToken`.

## Доктрина на алармите (не я разваляй)
- **„Празна нула" е лъжа, и се ГЕЙТВА** (`npm run degraded`). Липсващ `docker` не
  е „нула контейнера", липсващ `systemctl` не е „нула таймера", нечетима папка на
  nginx не е „нула сайта". Одитът пуска сървъра с ПРАЗЕН PATH и търси две неща:
  маршрут, който гърми, и маршрут, който връща празно БЕЗ признак, че данните
  липсват (`null`, `available:false`, `unknown`). Прегледаните изключения живеят
  в `REVIEWED` вътре в скрипта, с причина — храпов механизъм: нов мълчащ маршрут
  изскача веднага. Оттам излязоха: `ps` → „Вътрешна грешка" вместо „инсталирай
  procps", покритието на сайтовете → `total:0` при нечетим nginx, таймерите →
  празна таблица при липсващ systemctl.
- **Липсващ инструмент не е 5xx без име.** `runOk` отделя ENOENT (503 + `safe:true`
  + кой пакет го носи) от истинския провал на командата (502, чийто stderr си
  остава маскиран). Маската на 5xx в `server.js` пуска САМО `safe` съобщенията —
  те не издават вътрешности, а превръщат задънената улица в следваща стъпка.
- **Кой пази пазача.** Най-тихият провал не е „сървърът падна", а „наблюдателят
  замлъкна". Никоя вътрешна проверка не открива собствената си смърт, затова има
  три отделни неща: (1) **мъртвецът-ключ** (`alerts.heartbeatUrl`) — пинг след
  ВСЯКА успешна оценка към външен наблюдател, чиято аларма е самото МЪЛЧАНИЕ;
  (2) `health()` — възрастта на последната оценка, в панела над алармите, защото
  „няма аларми" значи различно нещо според това дали проверката върви; (3)
  `monitor:gap` — еднократно събитие, когато между две оценки е минало много
  повече от каданса (спрян процес, приспана машина).
- **Пингът на мъртвеца-ключ се ЗАПИСВА, не се предполага.** `post()` никога не
  хвърля (връща `{ok:false}`), значи „изстреляй и забрави" правеше DNS грешка,
  изтекъл URL и блокиран изход неразличими от успех — а панелът рисуваше зелено
  само защото полето е попълнено. `health().heartbeatOk` е зелено единствено при
  ДОКАЗАН пинг; провалът вдига `heartbeat:down`.
- **Условие, добавено към списъка СЛЕД цикъла, който го обхожда, е мъртъв код.**
  Точно това се беше случило със `stale:` — потискането на резолва работеше, но
  самата аларма „Липсва телеметрия" не можеше да пламне и човек гледаше аларми,
  висящи вечно без обяснение. Мълчаливият пазач е по-лош от липсващия.
- **Delta-сигналът е СЪБИТИЕ, не състояние** (`transient: true`). OOM, препълнена
  опашка, рестарт-цикъл, изхвърлени/отказани от Redis се мерят по разлика между
  две проверки; следващия път разликата е 0 и състоянието би пратило „Възстановено:
  Ядрото уби процес заради памет". Нищо не се е възстановило — просто не се е
  повторило, а лъжливото успокоение е по-скъпо от пропуснатата аларма.
- **Хистерезисът е СИМЕТРИЧЕН.** Пламването иска `sustainSamples`; отпадането иска
  `resolveSamples` (2). Иначе условие, което трепти около прага, прави безкрайни
  двойки „пламна/възстанови се" — и то без cooldown, защото резолвът не минава
  през него.
- **Повторението е съразмерно на времето за действие** (`repeatEvery`). Плосък
  час върху аларма с хоризонт седмици = стотици съобщения за един изтичащ
  сертификат/домейн/провалена проба. Бавните аларми напомнят веднъж на 24 часа.
- **„Аномалиите не будят човек" е механизъм, не коментар.** Тежест `info` не
  тръгва към каналите (`alerts.notifyInfo: false`) — стои в панела и в дневника.
- **Живите числа са в `body`, но и `title` се обновява.** Двигателят обновяваше
  само `severity`/`body`, значи „12.5% от заявките връщат 5xx" замръзваше от
  момента на пламване и си противоречеше с тялото на същия ред.
- **Известие, което не е стигнало, е липсващо известие.** `notify:down` е
  критично СЪСТОЯНИЕ (не събитие) — по каналите не може да се съобщи, че
  каналите са счупени, затова остава на екрана. Мери се само когато наистина е
  имало опит: известие, изцяло отсято по праг, не доказва нищо.
- **Прагът по канал не бива да яде „Възстановено".** Вдигането носи тежест `ok`
  (най-ниският ранг) — наивен филтър пуска „сървърът падна", но спира „сървърът
  се върна", което е най-лошата комбинация. Затова `passesSeverity` мери
  ПО-ТЕЖКОТО от текущата и предишната тежест (`wasSeverity`).
- **Изходящ адрес от браузъра не е „валиден URL".** Панелът върви като root на
  същата машина, на която живеят Redis, Postgres и самият панел; в облак
  `169.254.169.254` е метаданните на инстанцията. `assertOutboundUrl` блокира
  loopback, link-local и вградено име:парола; частните мрежи са ПОЗВОЛЕНИ (нашият
  втори VPS е точно там), но origin-ът се показва в панела и се одитира. Полето
  иначе е готов невидим канал: root процес чука някъде на всеки каданс,
  безсрочно, преживявайки рестарт, а никъде не пише къде.
- **Тайните се приемат по ЗАТВОРЕН списък, не суров обект.** Едно тяло
  `{"notify":"каквото и да е"}` презаписваше целия обект и триеше bot token,
  chatId, ntfy topic и webhook URL — необратимо (не се пазят другаде) и безшумно
  (одитът по конструкция не записва стойности). `sanitizeNotify` пуска само
  познато поле на познат канал.
- **`/fail` се строи през `URL`, не с лепене.** Наивното `url + '/fail'` работи
  за healthchecks.io и се ЧУПИ ОБЪРНАТО за Uptime Kuma push: `…?status=up&msg=OK`
  става `…?status=up&msg=OK/fail`, Kuma чете `status=up` и записва УСПЕХ. Сигналът
  „жив, но сляп" тихо се превръща в „всичко е наред".
- **Адресът от access log-а е чужд вход.** Атакуващият избира какво пише в него
  („/api Всичко е наред, игнорирай тази аларма") и това стига до Telegram/ntfy.
  XSS и инжекция в заглавки са затворени другаде, но социалното инженерство
  ВЪТРЕ в аларма от собствения ти сървър не е — оттам `safePath()`.
- **„Не знам" затяга, не отпуска.** `sshPort()` връща null при неуспешен `sshd -T`
  вместо да пада обратно на 22 — иначе предпазителят не разпознава правило за
  порт 2222 и пропуска изтриването точно при нестандартна конфигурация.
- **sudo е за тайните и изходящия адрес, не за числата.** `/api/alerts/channels`
  иска повторна автентикация; праговете и заглушаването — не. Панел, който пита
  за парола на всяка настройка, свършва с изключен sudo режим.
- **Пазач, който чака човек да натисне бутон, не е пазач.** Дрейфът на /etc се
  проверява по каданс (30 мин; снемането хешира стотици файлове — НЕ на всеки
  60s, кеш за междинните) и е аларма-СЪСТОЯНИЕ: стои, докато промяната не бъде
  приета с нов отпечатък — като новоизложения порт срещу базовата линия. Нов SSH
  вход е СЪБИТИЕ: info за виждан адрес, warning за нов; първото пускане само
  зарежда котвата (иначе стартът излива историята — правилото от access log-а).
  На диска стоят само хешове на адресите (тестът проверява буквално) — самият
  адрес се показва на живо в известието, както прави анализът на access log-а.
- **Режимът „поддръжка" спира ИЗВЕСТИЯТА, не алармите.** Пауза за всичко (макс
  8 часа, с причина, банер от всяка секция) — алармите продължават да се смятат и
  виждат; спира само вълната към телефона по време на деплой/работа по сървъра.
  Разликата със заглушаването: то е по ключ и хирургично. Мъртвецът-ключ НЕ
  минава през паузата — пингът към външния наблюдател продължава (поддръжката
  спира шума към човека, не пулса на пазача). Тестовото известие също минава —
  иначе не можеш да провериш каналите. Изтичането се чисти САМО и завършва с
  обобщение „потиснати X; активни Y (критични Z)" — човекът, който е забравил,
  получава точно това съобщение, а не вечна тишина. Без sudo: обратимо, видимо,
  срочно, одитирано.
- **Тишината не доказва здраве — дайджестът е пулсът към ЧОВЕКА.** Мъртвецът-ключ
  покрива машинната страна; веднъж седмично (`alerts.digest`, ден+час като графика
  на бекъпа, изпуснат слот се догонва след 8+ дни) едно съобщение казва „жив съм и
  ето какво видях" — 0 критични също е информация. Съставянето е ЧИСТА функция
  (тестваема без система); по каналите минава с `force` — покрай прага по канал и
  покрай `notifyInfo`, защото отчетът е изрично поискан, не инцидент. Езикът му е
  БЪЛГАРСКИ — напуска панела, а записите навън са на един език. Първото пращане
  чака слота (инсталацията не спами), под 6.5 дни от последното — мълчи дори в
  слота (пази от двойно пращане при рестарт в същия час).
- **Заглушаването е срочно и видимо.** Заглушената аларма продължава да се смята
  и да стои в панела — спира само известието, и то с краен срок (макс 7 дни) и с
  таван на броя (50; конфигът носи `passwordHash` и се пренаписва ЦЯЛ при всеки
  запис). Съвпадението е ТОЧНО: мълчаливият префикс правеше „заглуши `disk:/`"
  равно на „ослепи всички дялове", а ключ от една буква — целия регистър. Цяло
  семейство се заглушава изрично, със звездичка (`disk:*`).
  Безсрочното заглушаване е начинът да забравиш, че си сляп.
- **Един проблем = една аларма.** Дял на 97%, който се пълни за 5 дни, не е два
  проблема: прагът и прогнозата се СЛИВАТ в `disk:<mount>` с по-тежката тежест.
  Прогнозата обогатява текста със срока, но никога не смъква тежестта на прага.
- **Аларми по СИМПТОМ, не по причина.** „CPU 90%" при доволни потребители не е
  проблем. Затова първи стоят **PSI** (`/proc/pressure` — колко % от времето
  задачите СА ЧАКАЛИ ресурс) и **steal** (хостерът краде време). Праговете по
  CPU/памет са само резерва за ядра без PSI.
- **Прогноза преди праг.** „Дискът ще се напълни след 3.2 дни" е действено;
  „дискът е на 86%" не е. Прогнозата минава през Mann–Kendall гейт и **мълчи**,
  ако трендът не е значим — по-добре нищо, отколкото фалшива тревога.
- **Аномалиите не будят човек.** Те са с тежест `info` и служат за контекст при
  разследване. Аларма по аномалия е класическият източник на умора от известия.
- **Задържане + cooldown + „възстановено".** Праг трябва да се задържи N проверки;
  `sustain: false` е само за стабилните сигнали (паднала услуга, OOM, изтичащ
  сертификат, ro файлова система).
- **Преход, не състояние.** Аларма за read-only файлова система се вдига само при
  преход rw→ro. Дял, ro от самото начало (squashfs образ), е нечие решение — на
  живо това щеше да гърми 5 фалшиви критични при всяка проверка.
- **Burn-rate, не праг за наличност.** SLO алармата гледа СКОРОСТТА на харчене на
  бюджета за грешки през два прозореца (дълъг решава дали е сериозно, къс гаси
  бързо). И ДВАТА трябва да минат прага. Отгоре има твърд минимум лоши проби в
  късия прозорец (`slo.minBadShort`, по подразбиране 3) — иначе една мигнала проба
  вдига аларма. Цената е ~3 минути забавяне; съзнателна размяна срещу шума.
- **„Бавно" е ОТДЕЛЕН показател от „долу".** Сайт, който отговаря за 9 секунди,
  формално е наличен. Не сливай двете в един процент — губиш точно сигнала, който
  показва влошаване преди срива.
- **Новата грешка в журнала е събитие, не състояние.** Тя не се „възстановява" →
  минава през `event()`, не през активните аларми. Известява се само p≤3 (истински
  грешки) и само МАСКИРАНИЯТ шаблон — журналът съдържа произволен текст от интернет
  (`sshd: Invalid user <каквото напише атакуващият>`), а известието излиза навън.

## Езиците (BG/EN/IT)
- **Българският е ИЗТОЧНИКЪТ и КЛЮЧЪТ.** Никакви `nav.ports.title` ключове —
  ключът е самият български низ (gettext-стил). Три следствия: липсващ превод
  деградира до работещ български (не до счупен ключ на екрана); речникът е тройки
  `[bg, en, it]` в `i18n-dict.js` и паритетът е ПО КОНСТРУКЦИЯ (тестът проверява
  масива, не три файла); нула инструментиране на app.js — преводът живее в
  `el()`/`toast()` в ui.js, на ЕДНО място.
- **Динамичните низове се превеждат по ШАБЛОН**: числото + мерната единица стават
  маркер (`⟦0⟧`), „преди 3 мин" → „преди ⟦0⟧ мин". Разделителите в числото са само
  ВЪТРЕШНИ (`1.5`, `06:37`) — завършваща запетая е препинателен знак („eth0, значи"
  иначе я поглъщаше и шаблонът не съвпадаше, видяно на живо).
- **Сървърното съдържание СЪЩО се превежда — но само показването.** Сървърът
  навсякъде говори български: записите на диска (одит), Telegram/ntfy известията
  и изходът на задачите са ЗАПИСИ и напускат панела — езикът им е ЕДИН. Клиентът
  разпознава сървърния низ по трето стъпало шаблони, в които ДАННИТЕ (латинска
  дума/път/число) са маркери: „Продукт не отговаря: zabobovdol" →
  „Продукт не отговаря: ⟦0⟧". Ключовете се извличат от изходния код (`${…}` →
  маркер) и двете страни токенизират ЕДНАКВО — токенът не завършва на „.:,"
  (те са препинателни знаци; „zabobovdol:" иначе гълта двоеточието), а „/" също
  е данни („Дрейф/консистентност"). Съставните заглавия („Възстановено: X",
  „Провалена задача: X", „→ X") се превеждат по части, рекурсивно. Кирилска
  интерполация в сървърен шаблон (`${where}` = „всички интерфейси") НЕ става
  маркер — за нея се добавят конкретни варианти на ключа. Изключение остават
  суровите одиторски редове (key=… title=…), изходът на shell задачите и
  собствените имена на агентите — те са дословни записи/имена.
- **Смяната на език ПРЕЗАРЕЖДА** (`location.reload`), не пре-рендва: езикът е в
  стотици вече нарисувани възела, а състоянието е на сървъра. Изборът е в
  `localStorage` (`csd.lang`); статичният HTML се превежда веднъж при старт
  (`translateDom` — TreeWalker по текстовите възли, нула промени по маркировката).
- **Директен `textContent =` заобикаля превода.** Всичко текстово да минава през
  `el()`/`toast()`; ако няма как — увий в `t()`. Съставен низ (превод + данни) се
  СГЛОБЯВА от преведени части, не се превежда цял (`Последно: …`, `Корен …`).
- **Рънтайм обиколката е мерилото**: `window.__i18nMissing` събира непокритото;
  Playwright през всички секции на EN → списъкът е одитът на покритието. Статичен
  grep не вижда слепени/динамични низове.
- **Типография по език** (skill i18n-parity): BG „…“, EN "…", IT «…» + учтива
  форма (Lei). Техническите имена (ufw, systemd, vhost, Docker…) не се превеждат.

## Десктопът (незадължителен)
- **Изключен по подразбиране и НЕ стартира с машината.** Причината не е RAM
  (~1 GB при 16 GB е нищо) — а че жива графична сесия с браузър вътре е ВТОРА
  среда за изпълнение на машината. Пускането иска sudo; спирането — не (да не
  можеш да спреш нещо е най-лошият момент да си блокиран).
- **Клиентът НЕ влиза в `public/`.** noVNC/KasmVNC е ~1 MB чужд JavaScript;
  вкараме ли го, правилото „нула зависимости" престава да важи. Затова десктопът
  живее в контейнер, а панелът само го показва в рамка.
- **Единственият път навътре е през входа на панела.** Контейнерът слуша само на
  `127.0.0.1`, а браузърът стига до него през `/desktop/…` на самия панел —
  значи наследява сесията, 2FA-та и списъка с адреси. Публикуваш ли порта или му
  дадеш отделен vhost, целият модел пада.
- **Панелът си маха СВОИТЕ заглавки за тази пътека.** `x-frame-options: DENY`
  забранява рамкирането дори от същия произход (за същия произход трябва
  `SAMEORIGIN`), а `frame-ancestors 'none'` прави същото. Без това рамката е
  черна БЕЗ нито едно съобщение за грешка.
- **WebSocket-ът се прокси ръчно.** `node:http` не го прави сам, а VNC е
  WebSocket от първата до последната заявка. Автентикацията в `upgrade`
  обработчика е ЗАДЪЛЖИТЕЛНА — класическата дупка е заявките да са зад вход, а
  сокетът да не е. Nginx също иска `Upgrade`/`Connection` (панелът сам по себе си
  ползва SSE, не WS — тези редове са само заради десктопа).
- **`SUBFOLDER=/desktop/`** — префиксът се препраща КАКТО Е, не се реже.
  Контейнерът сам очаква да живее под подпапка; отрежеш ли го, вътрешните му
  връзки сочат в корена.
- **`deploy/desktop/desktop.env` е в `.gitignore`.** Паролата на десктопа е втори
  слой и живее до compose файла на сървъра (mode 600) — същото правило като
  `restic.env`.

## Портовете (карта на изложеността + смяна)
- **Изложеността е ТРИ състояния, не булево.** Старият изглед („Сигурност →
  Отворени портове") показваше адрес + процес — вярно и почти безполезно, защото
  не отговаряше на единствения важен въпрос: достъпен ли е този порт от интернет.
  Отговорът е сечение (на какво слуша сокетът × какво пуска ufw) и има трето
  състояние: **„не знам"**. То е задължително и се стига до него по два пътя —
  ufw не отговори, или ufw има правило, което не можем да преведем до порт
  (именуван профил). И в двата случая НЕ казваме „защитен". Панел, който твърди
  „защитен", когато не знае, е по-лош от панел, който мълчи — същата доктрина
  като при алармите.
- **`ss` не е даденост.** Минимален образ без iproute2 оставяше картата с три
  реда. Резервата е `/proc/net/{tcp,tcp6,udp,udp6}` — идиомът на продукта (метриките
  вече четат /proc директно), а не заобиколен път. Провалът на ДВЕТЕ остава
  ОТЛИЧИМ от „нищо не слуша": иначе картата казва „всичко е чисто" точно когато
  не знае нищо.
- **Адресът в /proc е шестнайсетичен с ОБЪРНАТИ байтове по думи от 4 байта.**
  `0100007F` е `127.0.0.1`, не `1.0.0.127`. Това е класическото място, където
  такъв парсер се пише грешно и после показва „изложен" за loopback.
- **Само слушащите.** TCP `st=0A` (LISTEN) и UDP `st=07` (UNCONN). Всичко останало
  в тези файлове е активна ВРЪЗКА, не порт, който чака — а картата е за чакащите.
- **PID-ът се намира по inode**, не с втора команда: `/proc/<pid>/fd/*` е връзка
  „socket:[<inode>]". Оттам идва и unit-ът (`/proc/<pid>/cgroup`) — тоест „какво
  да спра, за да затворя този порт" не изисква второ търсене.
- **Алармата е за ПРОМЯНАТА, не за състоянието.** „Порт 443 е отворен" не е
  новина — той трябва да е отворен. Затова има приета базова линия (`ports.json`,
  mode 600, преживява рестарт) и гърми само НОВО изложен порт, точно като
  `NRestarts`. Без приета линия панелът не залива човека, а кани да я приеме
  (`info`, веднъж на 7 дни). Ключът е `порт/протокол` — 53/udp не е 53/tcp.
- **Изчезналият порт е ИНФОРМАЦИЯ, не проблем** — но е информацията, която
  обяснява защо продукт е спрял да отговаря.
- **Тази секция само ПОКАЗВА.** Затварянето минава през „Firewall", където са
  предпазителят за SSH и одитът. Две места, които мутират стената, са едно място
  повече от нужното.
- **Панел, който не знае какво пази, е зелен по същата причина, по която е сляп.**
  „Уеб сървър" изброяваше ФАЙЛОВЕТЕ във `sites-available` — вярно и почти
  безполезно: 14 vhost-а и 3 health проверки изглеждат точно като 14 покрити
  сайта, защото за останалите 11 просто няма кой да пита. Липсващата проверка не
  гърми НИКОГА; тя мълчи, докато клиентът не се обади. Затова `coverage.js`
  сравнява `server_name` на ВКЛЮЧЕНИТЕ vhost-ове с `healthChecks`+`watchDomains`
  и показва разликата.
- **Health проверка към `127.0.0.1` НЕ покрива домейна.** Тя мери дали процесът е
  жив — не дали светът стига до него. Изтекъл сертификат, изтрит `server_name`,
  ufw правило и спрян CDN са невидими оттам (същият урок като синтетичната проба
  срещу access log-а). Затова се брои само проверка, чийто хост е реален домейн.
- **`www.X` и `X` са ЕДИН сайт.** Без нормализацията панелът предлага да следиш
  два пъти едно и също и списъкът губи доверие — а списък, който човек спира да
  чете, е равен на липсващ.
- **Домейнът за следене се сверява срещу РЕАЛНО намерените, не се приема от
  тялото.** Иначе това е „добави произволен изходящ адрес, който root процес да
  чука на всеки каданс" — точно заплахата, срещу която стои `assertOutboundUrl`
  при мъртвеца-ключ.
- **Разборът на nginx е нарочно ГРУБ.** Конфигът е пълноценен език (include,
  променливи, map) и тук не се строи парсер — вадят се `server_name` редовете.
  Пропуснат домейн значи „предлагаме по-малко", не „твърдим покритие, каквото
  няма"; закоментираните редове се режат ПРЕДИ разбора.
- **Смяната на порт е ЧЕТИРИ промени на четири места** и се чупи, защото хората
  правят три: `.env` → рестарт → vhost → `healthChecks` на панела. Забравеният
  vhost дава 502 при жив продукт; забравената проверка е по-коварна — не чупи
  нищо на потребителя, а чупи ДОВЕРИЕТО в алармите (критична аларма за напълно
  работещ продукт). Затова стъпката „health" я има ВИНАГИ и е последна.
- **`sed` по КЛЮЧ, не по число.** Анкерът е `^\s*(export\s+)?КЛЮЧ\s*=` — сляпото
  търсене на `3000` сменя и `TIMEOUT_MS`, и коментара. Записът се ПОТВЪРЖДАВА с
  `grep` след това; непотвърден запис е откат.
- **Планът не пипа нищо, прилагането носи откат в СЪЩИЯ процес.** Копие с
  суфикс `.преди-смяна-на-порт` преди всяка промяна, `nginx -t`/`caddy validate`
  преди reload, и проверка срещу НОВИЯ порт (до 30 s) — при провал откатът е
  функция, за да е един и същ по всички пътища. Разделиш ли ги, откатът зависи от
  това дали някой гледа.
- **`healthChecks` се обновява САМО при изход 0.** Задачата се следи и конфигът
  се пипа след успех — иначе неуспешна смяна оставя панела да вика порт, който
  никога не е заработил.
- **Порт под 1024 се предупреждава ПРЕДИ да е пипнато нещо.** Продукт под
  собствен потребител не може да го заеме и рестартът пада с EACCES.

## Особености, които е лесно да счупиш
- **SSE носи JSON, ВИНАГИ.** В SSE протокола `\r` е валиден край на ред → суровият
  текст губи carriage return-ите по пътя. Терминалът се разпада (курсорът не се
  връща в началото), лентите за напредък в логовете също. Затова `openSse().send()`
  прави `JSON.stringify` на всичко, а клиентът винаги `JSON.parse`-ва. Не „опростявай"
  обратно към суров текст.
- **Входът към PTY минава през опашка.** Браузърът праща по един клавиш; без
  опашка заявките се надпреварват и „top" стига като „tpo" (видяно на живо).
- **PTY без нативна зависимост.** `pty.js` пуска обвивката през `script -qfc`
  (util-linux) — това заделя истински TTY, затова htop/nano/sudo и Ctrl+C работят.
  Не подменяй със `spawn('bash')`: тогава няма TTY и всичко интерактивно умира.
- **Броят колони се МЕРИ, не се гада.** Сгрешена ширина = всяка TUI програма рисува
  в грешни колони.
- **Проверявай в БРАУЗЪР, не само по API.** Обзорът беше напълно счупен (масив от
  `<td>` вместо `<tr>`), а всички тестове минаваха. `el()` вече приема низове и
  вложени масиви, за да не може една такава грешка да изпразни цяла секция.
- **Терминалният рендер е наш.** `public/ansi.js` е малък VT100 емулатор (SGR,
  движение на курсора, изтриване, алтернативен екран). Изходът минава през
  екраниране → нула XSS от терминала. Не поддържа целия VT спектър — ако някога
  потрябва, алтернативата е xterm.js, но тя е външна зависимост.
- **`.env` редакторът пише ЧАСТИЧНО.** Приема `{ключ: стойност}`, не цялото
  съдържание — така маскираната стойност физически не може да презапише истинската
  (най-честият начин такъв редактор да изтрие тайните на продукцията). Пътищата са
  от ЗАТВОРЕН списък: произволен път в тялото би направил редактора „презапиши кой
  да е файл на сървъра" с приятен интерфейс.
- **DNS се проверява ПРЕДИ certbot.** Let's Encrypt гори лимита от 5 провала на час
  на домейн; после не издава дори при вече верен DNS. Проверката е задължителна, а
  не съвет — единственият байпас е `--staging`, който не пипа бойния лимит.
- **Webhook-ът НЕ деплойва.** Известява и толкова. Автоматичен деплой по webhook
  значи, че подправена заявка стартира код на сървъра по път, който заобикаля
  човека. Маршрутът е единственият без `guard()` — носи защитата си сам (HMAC,
  таван на тялото, дроселиран одит на отказите).
- **Всичко от GitHub минава през `cut`** (реже дължина + маха нови редове). Име на
  репо с вграден „\n" иначе рисува втори, престорен ред в известието.
- **Лимитите са drop-in, не редакция на unit файла.** Деплоят подменя unit-а;
  drop-in-ът оцелява, а `systemctl revert` го маха. Празната стойност се записва
  като `infinity` ИЗРИЧНО — пропуснатото поле оставя стария лимит в сила.
- **sudo пита само при мутация** (`SUDO_ON_WRITE`) — освен терминала, PTY и
  четенето на произволен файл (`SUDO_ALWAYS`), които са контрол над машината дори
  при GET (жив SSE поток = изпълнение на код; `/api/files/read` като root значи
  `/etc/shadow`, `/root/.ssh` и всеки `.env` на един GET разстояние). Ако и
  останалото четене питаше за парола, панелът щеше да пита на всяка втора секция,
  а изморената защита се изключва. Изключение: `.env` с `reveal=1` — то е GET, но е
  точно заплахата, срещу която sudo съществува. Записът на файл и редакцията на
  крон са изпълнение на код с една стъпка забавяне (пишеш unit/скрипт, после го
  пускаш от „Услуги") → и двете са в `SUDO_ON_WRITE`.
- **Списъкът с адреси е в `server.js`, ПРЕД рутера** — иначе покрива само API-то, а
  формата за вход и статиката остават видими и твърдението „скенер не стига дотам"
  е невярно. Единственото изключение е `/api/webhook/` (GitHub чука от чужди
  адреси и носи защитата си сам). Празен списък = ИЗКЛЮЧЕНО, а записът се отказва,
  ако списъкът не включва текущия адрес — иначе една грешка заключва собственика.
- **„Разследване" не твърди причинност.** Показва съвпадения по време и го КАЗВА
  на екрана. „Деплой 2 минути преди скока" е улика, не присъда — панел, който
  сочи виновник, се доверява точно когато не бива.
- **Времевата линия взема само МУТИРАЩИТЕ действия.** Префиксът не стига:
  `file.write` и `file.view` го споделят. Четенето се вади отделно (`READ_ONLY`),
  иначе линията се удавя в „някой отвори секцията".
- **Груповият избор оцелява филтъра — и броячът го казва.** „5 избрани", докато на
  екрана се вижда един ред, е капан; затова се брои от избора спрямо видимите
  чекбоксове (едни секции скриват редове с `hidden`, други изобщо не ги рисуват).
  Груповото СПИРАНЕ иска изписване на броя и изброява засегнатите.
- **Курсорът на access log-а хвърля първия ред САМО при скок.** Отместването от
  курсора е точна граница на ред; хвърлянето там изяжда истински запис при всяко
  следващо четене (видяно в тест). Ротацията се разпознава по inode (сменен файл)
  и по смаляване (copytruncate) — иначе четеш от средата на новия файл.
- **`ut=` разделя вината.** `$request_time` е ЦЯЛОТО време, което nginx е видял
  (бавен клиент, TLS, чакане за worker); `$upstream_response_time` е само
  приложението. Без разделянето всеки бавен адрес изглежда като бавен код и
  оптимизираш грешното нещо. Присъдата (`blameOf`) МЪЛЧИ под 200 ms — там
  разликата е измервателен шум.
- **TRAFFIC е четвъртият златен сигнал и се вижда САМО оттук.** Синтетичната
  проба чука от самата машина: при изтекъл домейн/DNS, ufw правило, изтрит
  `server_name`, спрян CDN или блокиран порт при доставчика тя вижда 200, а
  светът получава нищо. Единственият белег е, че access log-ът спира. Правилото
  е нарочно тъпо и затова надеждно — гърми само при ЯСЕН предходен трафик,
  паднал на НУЛА (тиха нощ и пресен старт мълчат); за бавен спад трябва история,
  каквато още нямаме.
- **5xx се броят от access log-а, не от пробата.** Пробата пита един адрес и
  вижда 200; потребителите в същия момент може да получават 500 на плащането.
  Броим само НОВОТО от последната проверка и само над минимум заявки; ПЪРВОТО
  четене само зарежда курсора — иначе стартът вдига аларма за 24 MB история.
- **Бавното се подрежда по p95, не по средно.** Адрес с 90% бързи и 10% ужасни
  заявки има по-ниско средно от равномерно бавен адрес — а потребителят усеща
  точно опашката. Средното е начинът бавният отчет да остане невидим.
- **IP-тата не влизат в състоянието на диска.** Показват се на живо (законен
  интерес — сигурност), но `accesslog.json` пази само отмествания. Тестът го
  проверява буквално.
- **Бекъпът се следи по ВЪЗРАСТ, не по „мина ли".** Спрял крон не вдига грешка;
  липсата на файл също. Плюс подозрително малък файл — той е по-опасен от
  липсващ, защото изглежда като успех.
- **Бекъпът се ПРАВИ, не само се следи.** Панелът имаше аларма за възраст, проба
  за възстановяване и бутон — но нищо не пускаше снимката само, тоест вдигаше
  критична аларма за проблем, който сам може да реши. Часът е ФИКСИРАН (нощем), не
  „на всеки 24 часа от последния път" — иначе бекъпът пълзи през деня и някой ден
  пада върху деплой. Първото пускане чака нощния час нарочно (инсталацията не бива
  да вдига двучасова задача върху сървър, който човекът точно сега настройва), а
  изпуснат час се ДОГОНВА над двоен каданс — иначе спрян в 03:00 панел чака цял ден
  и при два пропуска бекъп просто няма.
- **Зает ексклузивен ключ не е провал на графика.** `jobs.start` хвърля 409, докато
  тече проба или архив на томове. Записването му като провал би вдигнало фалшива
  критична аларма И би отложило истинския бекъп с цял каданс.
- **Включен график, който не се пуска, е отделна аларма** (`backup:sched-stale`).
  Той е по-опасен от изключения, защото ИЗГЛЕЖДА като покритие. Изключеният е `info`
  веднъж на 7 дни — не буди човек, но не мълчи.
- **`Number(null)` е 0, не „липсва".** `"atHour": null` (какъвто ред пише всеки
  инструмент за непопълнено поле) тихо местеше бекъпа на ПОЛУНОЩ вместо на
  подразбирането. Стойност от конфига се проверява с `Number.isInteger`, не се
  коерцира. Обратно, `everyHours: 0` пада на 24, НЕ на клампнатата 1 — пълен дъмп на
  всеки час е по-лошо от сгрешеното число.
- **3-2-1: изнасянето иска TLS, без изключение за частна мрежа.** Одитът е
  метаданни; дъмпът е ЦЯЛАТА база (за medqr — чл. 9 GDPR). `http://` peer се
  ОТКАЗВА (освен loopback, за тест) вместо да работи тихо и да изглежда успешно.
- **Приемникът не вярва на подателя.** `content-length` е ЗАДЪЛЖИТЕЛЕН, за да се
  провери свободното място ПРЕДИ записа (иначе „бекъпът" сваля и резервната
  машина); хешът се сверява и несъвпадащото копие се ИЗТРИВА (копие, за което не
  знаем дали е цяло, приспива); името и възелът минават през затворен списък, защото
  влизат в път. Node сам слага `content-length` при `end(buffer)` — клонът 411 се
  тества със суров chunked сокет.
- **Панелът снима и СЕБЕ СИ — шифрирано.** Конфигът (тайни, които не съществуват
  никъде другаде) + state влизат в нощния бекъп като `panel-*.tar.gz.enc`
  (openssl aes-256-cbc, pbkdf2). Ключът минава през env (`CSD_PANEL_KEY`), НИКОГА
  през shell реда — той влиза в одита и в изгледа на задачата. Ключът е в конфига,
  а конфигът е в архива → при мъртъв диск загива с него: показва се (зад sudo,
  одитирано) за преписване ИЗВЪН машината. `offsite/` и `restore/` се изключват
  (рекурсия + чужди дъмпове). Възстановяването е СЪЗНАТЕЛНО ръчно — презаписва
  тайните на живия панел; панелът показва командата, не я изпълнява.
- **Чуждите копия живеят ОТДЕЛНО** (`<stateDir>/offsite/<възел>/`). Смесени със
  собствените, чуждият дъмп става „най-новият бекъп" на тази машина и гаси алармата
  за остарял СОБСТВЕН бекъп — същият капан като с том-архивите. Папката се извежда
  от `stateDir`, не е закована: закованият път пишеше в живата `/var/lib` и от
  тестовете (тестови възли изникнаха в таблицата на панела).
- **Прогнозата за диска и „кой яде диска" са двете половини на един отговор.**
  „Ще се напълни след 3.2 дни" без „ето кои са тези 40 GB" оставя човека на SSH
  промпт да налучква с `du`.
- **`--max-depth` ограничава ОТПЕЧАТВАНЕТО, не обхождането.** `du -d1 /` пак минава
  през цялото дърво — на пълен диск минути. Затова сканирането е фонова ЗАДАЧА с
  кеширан резултат и дата, не заявка: секция, която виси четири минути, човек не
  отваря втори път.
- **`-x` / `-xdev` е задължително.** Без него сканирането на „/" влиза в `/proc`,
  `/sys` и всеки монтиран том и брои едни и същи байтове по няколко пъти.
- **Прекъснатото сканиране НЕ се показва като пълно.** Скриптът пише маркер за край;
  без него (или при изход ≠ 0) резултатът е „ЧАСТИЧНО", а не отговор с половин
  истина. Същата доктрина като третото състояние при портовете.
- **Кореновите пътища са ЗАТВОРЕН списък.** Произволен път прави панела „изброй ми
  имената на всички файлове като root" с приятен интерфейс — същата заплаха като
  редактора на `.env` с произволен път. Съвпадението е ТОЧНО, не по префикс, иначе
  `/var/../root/.ssh` минава.
- **`docker system prune` го НЯМА и няма да го има.** `-a --volumes` трие томове с
  живи данни (качени файлове, бази) и е най-честият начин човек да си направи
  инцидент, докато „чисти място". От тук се пуска само `docker builder prune` (само
  build кешът — няма как да изтрие данни); изтриването на образи/томове е поименно,
  от секция „Docker".
- **„Кой яде диска" и „какво може да се освободи" са РАЗЛИЧНИ въпроса.** Първият
  казва КЪДЕ отиват байтовете; вторият — кои от тях са боклук. Човек на пълен диск
  в 3 сутринта иска второто. В `reclaim.js` влиза САМО това, което по конструкция
  не може да е данни: кеш, който се пресваля, вече ротирани логове, копия от самия
  деплой. Всичко, за което трябва да се мисли „а дали не ми трябва", стои ИЗВЪН
  списъка и се трие поименно от своята секция, с контекста пред очите.
- **Docker томове, спрени контейнери и `/tmp` ги НЯМА в чистенето и няма да ги
  има.** Том е данни; спрян контейнер може да е спрян нарочно; в `/tmp` жив процес
  държи файлове точно сега. „Почистих" е най-честият увод към инцидент.
- **Живият лог не се трие — това дори не освобождава място.** Файлът е отворен от
  процес; докато той го държи, `df` не мърда, колкото и да си изтрил. Затова
  съвпадението е само по АРХИВНИ имена (`.gz`, `.xz`, `.1`, `.old`).
- **Пътищата за триене минават през allowlist ДВА пъти** — веднъж при откриването,
  веднъж преди командата. Стойността идва от нашия код, но между двете има HTTP
  заявка, а всичко, минало през мрежата, е чужд вход. Клиентът праща само ИМЕ НА
  КАТЕГОРИЯ; кои файлове влизат в нея решава сървърът, наново. Иначе това е
  „изтрий каквото ти кажа като root" зад приятен интерфейс.
- **Размерът се смята с ЕДНО извикване, не с хиляди.** `find … -printf '%s'` вместо
  4000 отделни `stat`, `du` паралелно вместо в цикъл: разликата е между 200 ms и
  половин минута, а секция, която виси, човек не отваря втори път.
- **Свиването на журнала иска sudo.** То ТРИЕ логове — точно това прави човек, който
  заличава следи, и точно тази история изхранва „нова грешка в журнала".
- **Месечният трафик се НАТРУПВА по разлики, не се чете.** Броячите в
  `/proc/net/dev` се нулират при рестарт — абсолютната стойност не е месечен сбор,
  а наивното изваждане след рестарт дава МИНУС и сборът тръгва надолу. Нулирането
  се разпознава изрично (`cur < last`; тогава текущата стойност Е разликата) и се
  брои видимо, не мълчаливо.
- **Броят се само ФИЗИЧЕСКИТЕ интерфейси.** Трафикът на контейнер минава и през
  `docker0`/`veth*`, И през `eth0` — сборът от всички брои всеки байт двойно и
  панелът вдига аларма за квота на половината път. По подразбиране се мери само
  ИЗХОДЯЩИЯТ (Hetzner таксува само egress); месецът е по UTC, както таксува хостерът.
- **Прогнозата за квотата МЪЛЧИ през първите 10% от месеца** — на 2-ро число 3%
  употреба се проектират до 45%, а един ден с деплой изкривява всичко. Пропорция,
  не Theil–Sen: месечният сбор е монотонен по конструкция, тренд-тест не носи нищо.
- **Числото е ДОЛНА граница и това се КАЗВА на екрана.** Спрян панел не брои;
  трафикът между последната проба и рестарта се губи. Панел, който представя своя
  сбор за фактурата на хостера, лъже точно когато човек взема решение по него.
- **Квота-картата се рисува ПРЕДИ проверката за access log** — тя не зависи от
  nginx, а ранният return иначе я скрива на всяка машина без уеб сървър.
- **Пробата за възстановяване се планира по каданс, проверяван всеки час.**
  `setInterval` за 30 дни не преживява рестарт, а сървър, който се рестартира
  месечно, никога не би я пуснал. Резултатът се записва при ПРИКЛЮЧВАНЕ на
  задачата — „последна успешна проба" трябва да е факт, не намерение.
- **Flapping се мери по РАЗЛИКАТА в `NRestarts`.** Общият брой расте вечно и
  казва само, че услугата някога е падала. Услуга без предишна снимка не гърми.
- **Възстановяването на том първо ИЗПРАЗВА, после разархивира.** tar върху
  непразен том оставя файловете, създадени СЛЕД снимката — смес от две състояния,
  която изглежда като успех (същият урок като WAL/SHM при SQLite). Защитната
  снимка на ТЕКУЩОТО е преди всичко друго (не стане ли — нищо не се пипа), откатът
  е в СЪЩИЯ скрипт, а рестартът на спрените контейнери е в `trap EXIT` —
  включително по пътя на провала. За bind папка целта се ДОКАЗВА по краткия хеш в
  името на архива (иначе uploads на един продукт се излива върху друг), а
  `assertRestoreDir` отказва път под 2 нива — `find -delete` върху „/" или „/opt"
  не бива да е изразимо.
- **Възстановяването на SQLite не е `cp`.** Три неща го чупят тихо: WAL/SHM от
  СТАРАТА база остават до новия главен файл и SQLite ги „възпроизвежда" отгоре
  (смес от две бази) → трият се изрично; `cp` като root оставя root-owned файл и
  услугата под собствен потребител пада с „readonly database" → собственикът и
  правата се четат ПРЕДИ презаписа и се връщат след него; презапис под жив процес
  е повреда → услугата се спира и пуска (по избор, но силно препоръчано). Стартът
  ѝ не проваля задачата — данните вече са върнати, провалът се КАЗВА.
- **Postgres: `ON_ERROR_STOP=1` + `--single-transaction`.** По подразбиране `psql`
  ПРОДЪЛЖАВА след грешка и излиза с код 0 — половин върната база рапортува
  „✔ Готово". Дъмпът пък носи `--clean --if-exists`, иначе връщането в непразна
  база налива в СТАРИТЕ таблици и получаваш слята база, която изглежда наред.
- **`ufw delete` по номер има два капана.** Номерата се ПРЕМЕСТВАТ след всяко
  изтриване (затова се сверява `expect` — текстът, който човекът е видял), а
  правилото за SSH не изглежда по никакъв начин особено (затова е зад изричен
  `force`, като предпазителя при включване на стената).
- **„Колко процента" е грешният въпрос за `/boot`.** Дялът е ~1 GB, ново ядро иска
  ~120 MB, а `apt` разопакова НОВОТО, преди да махне старото — за миг трябват две.
  Затова прагът е в МЕГАБАЙТИ (250 MB резерв), не в проценти: `/boot` на 78% може
  вече да е фатален, докато коренът на 78% е спокоен. Общата дискова аларма по
  конструкция не може да го хване. Ефектът е най-тихата повреда, която имаме:
  машината мълчи с месеци и после се оказва без НИТО един ъпдейт за сигурност.
- **Прекъснатият dpkg се чете от `dpkg-query`, не от `dpkg --audit`.** `--audit` е
  човешки формат: параграф с обяснение, следван от списъка, и ДВЕТЕ части са с
  отстъп — всеки филтър „ред с отстъп = пакет" хваща и думи от изречението
  (`probably`, хванато в тест). `${Status}` е три полета и третото казва точно.
  „Наред" са ДВЕ състояния: `installed` и `config-files` (пакет махнат, конфигите
  оставени — съзнателен избор, не повреда).
- **„Не знам" НИКОГА не значи „действай" — и това не е стилистика.** `uname -r`
  се проваля (минимален контейнер, счупен PATH) → `classifyKernels` получава
  `current: null`, а наивното „всичко освен най-новото" тогава предлага да
  изтриеш ЯДРОТО, КОЕТО ВЪРВИ. Машината не се вдига, а панелът също не се вдига,
  за да го поправиш. Затова без известно текущо ядро списъкът за махане е ПРАЗЕН
  и се КАЗВА, че не знаем. Същото за `dpkg-query` и `apt-mark`: провалена команда
  дава `null`, не празен списък — `{broken: []}` е панелът, който твърди „dpkg е
  в ред", без да е питал.
- **Чистенето на ядра е ПОИМЕННО и пази две.** Никога `autoremove` на едро (маха и
  чужди пакети); никога текущото (върви в момента) и никога най-новото (то е
  следващото при рестарт) — махнеш ли ги, машината не се вдига, а панелът също не
  се вдига, за да го поправиш. Сортирането е по ЧИСЛО: `6.8.0-40` е по-ново от
  `6.8.0-9`, а лексикографски е обратното. Иска sudo.
- **Картата „може ли да се обновява" се рисува ПРЕДИ ранния return за „apt
  недостъпен".** Точно когато apt е счупен, списъкът с пакети е празен — и ако
  диагностиката е след проверката, тя изчезва именно в случая, за който е
  направена. Същият капан като с квота-картата и access log-а.
- **apt върви с `NEEDRESTART_MODE=a`.** На Ubuntu 22.04+ `needrestart` спира по
  средата с пълноекранен въпрос; няма кой да отговори и задачата виси до таймаута.
- **Дъмпът на базата НЕ е пълен бекъп.** Записът в базата сочи към файл в том
  `uploads`, който `pg_dump` не пипа — при възстановяване получаваш цели данни и
  счупени препратки. Томовете са отделно действие. Базите се пропускат ИЗРИЧНО
  (суров tar на жива база е непоследователен) и пропускането е ВИДИМО в изхода.
- **Томът се архивира през контейнер** (`docker run -v <том>:/src:ro`), не по
  `/var/lib/docker/volumes/...` — този път е вътрешна подробност на Docker и се
  мени между драйвери.
- **Името на архива носи къс хеш от пълния път.** Нормализирането е загубено:
  `/opt/app/uploads` и `/opt/app_uploads` дават еднакъв низ и вторият архив тихо
  презаписваше първия в един и същи запуск (хванато в тест).
- **Redis изхвърля ключове ТИХО.** При `allkeys-lru` и опрян таван освобождава
  памет, като трие — няма грешка, няма ред в лога, услугата е жива. Единственият
  белег е `evicted_keys`; следи се по РАЗЛИКА. Тежестта на „пълна памет" зависи
  от политиката: с eviction е warning (работи, но губи), с `noeviction` е
  critical (записите започват да връщат грешка).
- **Статичен сайт зад Caddy иска `host` в health проверката.** Той се разпознава
  по домейн, не по порт — заявка към `127.0.0.1` без правилен Host попада в сайта
  по подразбиране и „проверката" мери чужд сайт.
- **Хеш-веригата на одита сама покрива само СРЕДАТА.** Последният ред няма
  следващ, който да го провери, а отрязаните редове в края оставят вътрешно
  последователна верига — проверката казваше „наред" точно след класическия
  анти-форензичен ход. Затова има котва (`audit.head.json`: брой + хеш на
  последния). Ротацията нулира брояча — тя е законно скъсване.
- **Всяка навигация получава СВЕЖ `#view` възел** (`go()` клонира и подменя).
  Бавна секция (напр. „Ъпдейти", която чака apt) иначе се дорисува закъсняло и
  замазва секцията, към която вече си отишъл — видяно на живо: отваряш „Задачи",
  а вътре стои списъкът с пакети. Работи за всички секции наведнъж, защото
  всяка взема `view` ПРЕДИ първото `await`. **Ако пишеш нов render, вземи `view`
  в началото** — заявка след await ще хване новия възел и състезанието се връща.
- **Иконите на действията се подменят в ui.js, не по call-sites.** Бутон, чийто
  текст ЗАПОЧВА с глиф от `GLYPH_ICONS` (👁 ✉ ▶ ⟳ 🔑 …), получава `<img>` от
  `public/icons/act-*.png` автоматично — след превода, затова ключовете в
  `i18n-dict.js` остават С глифа (смениш ли ключа, превод няма). Навигацията НЕ
  минава оттук (иконата ѝ е отделен `span.ico`) — тя чака своя комплект nav-*.
  Нов бутон с водещ глиф от списъка получава икона даром; глиф по средата на
  текста и статусните знаци (✓ ⚠ ●) остават текст нарочно.
- **Инлайн `var(--…)` в app.js трябва да съществува в `style.css`.** Няма
  инструмент, който да го хване: несъществуваща променлива прави текста прозрачен,
  без грешка в конзолата. Имената са `--txt`, `--txt-dim`, `--danger`, `--warn`,
  `--ok`, `--line` — не `--fg`/`--bad`/`--dim`.
- **Копие на конфига преди всеки запис — атомарността не стига.** `tmp → rename`
  пази от ПРЕКЪСВАНЕ (ток по средата на записа), но не от ЛОГИЧЕСКА грешка: код,
  който запише валиден, но погрешен конфиг, унищожава `passwordHash`,
  `sessionSecret`, `peerToken`, токените за известия и ключа за бекъпа — тайни,
  които по конструкция не съществуват никъде другаде (нощният шифриран бекъп е до
  24 часа стар). `.bak` се прави САМО от файл, който се чете като валиден конфиг:
  иначе втори пореден лош запис презаписва и спасителното копие с боклук, а
  копие, за което не знаеш дали е цяло, е по-лошо от липсващо.
- **Провалът при СТАРТ е законен, stack trace-ът — не.** Човекът го чете в
  `journalctl` след неуспял рестарт; там му трябва какво е счупено, къде е файлът
  и коя команда го проверява — не пътят през модулния зареждач на Node. Пълният
  стек остава зад `CSD_TRACE=1`.
- **Управлението на сесиите съществуваше ЦЯЛО, но без нито един бутон.** Списък,
  поименна отмяна, отмяна на всички, преживяваща рестарт (`revoked.js`) — всичко
  беше в backend-а и минаваше през smoke теста, а „кой е влязъл в панела ми и как
  да го изхвърля" оставаше въпрос без екран. Функция без интерфейс е равна на
  липсваща: непозната сесия е сигнал за пробив, но само ако някой може да я види.
  Затова API маршрут, който `app.js` никога не вика, е находка, не подробност.
- **Конфигът се пише от кода** (`saveConfig`) при 2FA и настройки за аларми —
  атомарно, mode 600, вложено сливане. Не презаписвай целия файл наивно, ще
  изгубиш тайните.
- **Паметта за СЪБИТИЯТА изтича — иначе расте, докато панелът върви.**
  `transientSeen` пази „кога го видях за последно", за да не се повтори
  известието. Но ключът на някои събития носи ВРЕМЕТО в себе си
  (`ssh:login:<хеш>:<ts>` е нов при всяко влизане), значи картата растеше без
  край: ~3600 записа на година при десет влизания на ден, десетки хиляди при
  брутфорс с успели опити. Запис, по-стар от `max(24 ч, 10 × cooldown)`, вече не
  влияе на НИТО едно решение — държан е само защото никой не го е махнал. Таван
  500 е вторият предпазител. Този клас теч не се забелязва: той не чупи нищо,
  просто расте.
- **Тяло, което не е JSON ОБЕКТ, е 400 — не 500.** `null`, `0`, `"низ"` и `[]` са
  валиден JSON, но всеки маршрут после прави `body.поле` и получава TypeError.
  Отхвърля се в `readJson`, на едно място.
- **„Записано" трябва да значи ЗАПИСАНО.** `/api/alerts/settings` приема ЗАТВОРЕН
  списък полета (вложеният обект е защитата срещу презаписване на тайни), но тяло
  с непознат формат минаваше през него без нито едно приложено поле и връщаше
  `ok: true`. Човекът вижда „готово", прагът е стар, и следващият въпрос е „защо
  алармата пак гърми". Сега отговорът носи `applied[]`, а нула приложени полета е
  400 с обяснение какъв формат се очаква.
- **Целите за пръст растат САМО на тесен екран.** WCAG 2.2 (2.5.8) иска 24×24 CSS
  px и това беше спазено — но 24 е ПРАГЪТ, не удобството (Apple: 44pt, Material:
  48dp). Панелът се отваря най-често когато нещо гори и човекът е с телефон в
  ръка, затова под 820px бутоните стават 38px. Пипа се padding/min-height, НЕ
  font-size: шрифтът е част от плътността на информацията.
- **Всеки `<select>` носи `aria-label`.** Без него екранният четец казва само
  „падащо меню" — без КАКВО се избира (WCAG 3.3.2, ниво A). Намерено с реален
  обход, не с преглед на кода.
- **Невалидният ВХОД не бива да дава 5xx.** Системните грешки от `fs`
  (`ENOENT`, `ENOTDIR`, `EACCES`) нямат `status` → рутерът ги вдигаше като 500
  „Вътрешна грешка". Освен че лъже за произхода (наша грешка, когато е на
  подателя), е и вредно: 5xx влизат в SLO и хранят алармата за процент грешки —
  бот, който чука `/api/files?path=…`, вдигаше КРИТИЧНА аларма за напълно здрав
  панел. Преводът errno→статус е на ЕДНО място (`J()` в `routes.js`), не във
  всеки модул. Проверено с 252 злонамерени комбинации; регресията е в smoke.
- **Пробата по договор НЕ хвърля — тя връща „не работи" и защо.** Node отказва
  заявка с нов ред в пътя (`ERR_UNESCAPED_CHARACTERS` — неговата защита срещу
  инжекция в заглавки, и тя работи), но хвърля СИНХРОННО, извън Promise-а:
  без улавяне пробата не връщаше резултат, а сриваше маршрута с 500.
- **Аларми = промяна на състояние**, не всяка проверка. Праговите правила искат
  задържане N проверки; `sustain: false` е за стабилните (паднала услуга, изтичащ
  сертификат). Cooldown пази от спам; „възстановено“ също се известява.
- **Уеб конфигът се валидира преди reload** и се връща при провал — същият патърн
  като `autodeploy.sh`. Никога не презареждай без `nginx -t` / `caddy validate`.
- **Rollback** ползва `RELEASE_DIR` в `deploy/autodeploy.sh` (разгръща съществуващ
  release без разопаковане). Чистенето на стари releases пази текущия.

## Проверка в браузър (задължителна за промени по `public/`)
```bash
CSD_CONFIG=/tmp/dev.json node server.js &     # или npm run dev
# Playwright е глобален в средата — не се добавя към продукта (нула зависимости):
node -e "import('/opt/node22/lib/node_modules/playwright/index.mjs')…"
```
Внимание: `waitUntil: 'networkidle'` **никога не настъпва** — SSE потокът стои
отворен по дизайн. Ползвай `domcontentloaded`.

## Тестове
380 теста, `node --test`, без мокове на системата — тестват се само детерминистични
чисти функции: пароли/сесии, TOTP (с контролните вектори на RFC 4226), парсване на
`/proc`, рутера, allowlist-ите (unit имена, архиви, ufw правила, compose, dump),
историята, сливането на конфига, файловия запис, SLO математиката (бюджет,
burn-rate, защитата от една мигнала проба), маскирането на журнала (тайни/PII не
излизат в известие) и целия ANSI емулатор (вкл. екранирането срещу XSS).
`smoke.test.js` вдига ИСТИНСКИ сървър и минава по всички GET маршрути — той е
единственото, което хваща липсващ `import` в `routes.js` (`node --check` не го вижда).
Живите системни извиквания се проверяват ръчно на живо.
