# CLAUDE.md — erp-ascensori/

ERP Ascensori Enterprise — гестионал за фирми по поддръжка/монтаж на асансьори.
**Целият UI е на италиански**; коментари/комити — на български. Схема v3.0 по
`docs/` документацията (24 таблици · 13 енумерации · 7 нива достъп · 9 статуса).

## Стек и команди

Next.js 15 App Router · React 19 · TS strict · Prisma + **PostgreSQL 16** ·
Tailwind · Zod · jose · Recharts. Path alias `@/*`.

```bash
npm run dev / build / start
npm run lint && npm run typecheck && npm test   # качествена порта (задължителна)
npx prisma db push && npm run db:seed           # локална база + демо данни (IT)
npm run scadenze:check                          # автоматизмът за сроковете (cron 24h)
npm run retention                               # прочистване по срок (cron седмично)
bash scripts/setup-env.sh                       # генерира тайните за продукция
docker compose up -d --build                    # разгръщане (виж DEPLOY.md)
npm run test:int                                # интеграционен пакет (реална база + сървър)
npm run test:e2e                                # E2E през браузър (Playwright)
npm run webhook                                 # доставя известията (cron 5 мин)
npm run verifica:backup -- <файл>               # РЕАЛНО възстановяване на бекъпа
```

Демо вход след seed: `master@erp-ascensori.local` / `Ascensori!2026` (по един
акаунт на всяко от 7-те нива — същата парола).

## Твърди правила на домейна (не ги чупи!)

- **Нивото на достъп се проверява ОТ СЪРВЪРА на всяка заявка** (`richiedeRuolo()`
  в `src/lib/auth.ts`). Скриването на бутони в UI не е защита. Йерархия
  MASTER(1) > ADMIN(2) > DIREZIONE(3) > RESPONSABILE(4) > TECNICO(5) >
  OPERATORE(6) > CLIENTE(7) — по-ниското число включва правата на по-високото.
- **StatoOrdine минава само по позволените преходи** (`src/lib/workflow.ts` —
  таблицата от документацията, дословно). Всеки преход пише в `storico_stati`
  + audit `STATE_CHANGE` в транзакция.
- **Тоталите не се пишат на ръка**: при всяка промяна на voce се вика
  `ricalcolaPreventivo/ricalcolaFattura` (`src/lib/totali-db.ts`). Парите се
  смятат в **цели центесими** (`src/lib/totals.ts`), half-up — никакви float.
  Входът приема точка И запетая (IT). **За SDI ДДС-то се смята по АЛИКВОТА**
  (`riepilogoIva` в `totals.ts`), не сумирано по редове: SDI сверява
  `ImportoTotaleDocumento` с `DatiRiepilogo` и отхвърля разлика от един цент.
  Редовете на fattura/preventivo са променими само в определени статуси
  (`statiModificabili` в `voci.ts`: fattura=BOZZA, preventivo=BOZZA/INVIATO).
- **Giacenza-та се движи само през движения** (`/api/movimenti`, в транзакция).
  USCITA под нула се отказва; RETTIFICA е подписана корекция.
- **Audit-ът е неизменим**: всяка редица е подписана HMAC-SHA256
  (`src/lib/audit-hmac.ts`; подписът покрива и ip/userAgent), маршрути за
  промяна/изтриване НЕ съществуват. Проверка: POST `/api/audit/verifica`.
  `scriviAudit(opts, tx)` приема транзакционен клиент — критичните операции
  (STATE_CHANGE) пишат одита В СЪЩАТА транзакция; без подаден `tx` си отваря
  своя (`pg_advisory_xact_lock` извън транзакция не пази нищо).
  **Веригата** (`hmacPrecedente`, канон v3) лови и ИЗТРИВАНЕ на ред. Три неща
  не са по избор: добавянето е сериализирано с advisory lock **по фирма**;
  подредбата е по монотонен `seq`, не по `createdAt` (две вписвания в една
  милисекунда се сортират произволно); веригата е **по фирма**, иначе
  прочистването по срок в едната чупи другата. `AUDIT_HMAC_KEY_PRECEDENTE` се
  приема САМО при проверка, никога при подписване.
- **Вход**: bcrypt 10 rounds; 5 неуспеха → 15 мин блокада; refresh token само
  като SHA-256 хеш в базата, ротира се и се нулира при logout. Rate limit-ът е
  **по акаунт** (`login:<email>`), не по IP: без доверено прокси IP-то се подправя
  с хедър, а споделен ключ би позволил на анонимен да заключи входа за цялата
  фирма. По IP стои само много по-висок глобален таван.
- **Електронната фактура е ФАЙЛ, не изпращане.** `src/lib/sdi/` прави FatturaPA
  1.2.2 XML (`GET /api/fatture/:id/xml`; `?controlla=1` = само проверка).
  Подписът, подаването към SDI и conservazione a norma са ИЗВЪН продукта — в
  описанието към клиента това е разликата между „изготвя файла" и „издава
  фактури" (виж `docs/legale/README.md`). Черновата не се изнася: подаден
  документ е издаден и номерът му е изразходван. Сторното е `TD04`, не
  отрицателна фактура. Валидаторът е ЕДИН (`validaPerSdi`) и се ползва и от
  интерфейса, и от експорта — две истини за реквизитите се разминават.
- **Фискален архив**: издадена фактура не се трие — сторнира се (STORNATA).
  Референцирани анагрифики не се трият (FK ги пази → 409) — деактивират се.
- **Автоматизми**: `scadenze-runner.ts` — прагове 90/60/30 (флагове еднократно),
  цветен статус на автопарка (rosso <15 дни, giallo <45), preventivi → SCADUTO,
  fatture → SCADUTA. `retention-runner.ts` — ЕДИНСТВЕНИЯТ път, по който редове
  напускат одита: 6 месеца за LOGIN/LOGOUT (Provv. Garante 27.11.2008, в сила по
  чл. 22, ал. 4 D.Lgs. 101/2018), 10 години за следите по ФИСКАЛНИ ентитети
  (бял списък `ENTITA_CONTABILI`, чл. 2220 c.c.), 24 месеца за всичко останало
  (чл. 5(1)(д) GDPR), 90 дни за телеметрията. Непознат ентитет получава
  КРАТКИЯ срок — за данните безопасната посока е обратната на фискалната.
  И двата автоматизма пишат следа в `automatismi_run` (dead-man я чете).
- **RLS е ВТОРАТА линия на изолацията, не първата.** Политиките `tenant_isolation`
  (22 таблици, `FORCE ROW LEVEL SECURITY`) се задават с `SET LOCAL app.tenant_id`
  през `conRls` (`src/lib/rls.ts`) — Prisma не връзва връзка за цялата HTTP
  заявка, затова заявка БЕЗ поискан обхват минава през политиката. Тоест RLS
  пази пътищата, които заявяват обхват (цялата CRUD фабрика), и **не замества**
  `filtroTenant`. Ролята на приложението **не бива да е суперпотребител** —
  суперпотребителят заобикаля политиките безусловно, дори при FORCE; миграцията
  я понижава, а `/api/readyz` показва дали слоят е реално активен.
- **„Заличаване" по чл. 17 = АНОНИМИЗАЦИЯ, не изтриване** (`src/lib/gdpr/`).
  Правото се сблъсква с чл. 2220 c.c. (10 г.) и е изключено от чл. 17(3)(б):
  пада ЛИЦЕТО, остава СЛЕДАТА. Планът (`piano.ts`) е чист и тестван, показва се
  на човека преди натискане и носи разпоредба за всяко запазено нещо; след
  записа `residuiPersonali` проверява — остатъчно поле дава 500, а не тихо
  „готово". Одитът НЕ се пипа (редакцията би счупила веригата) — излиза сам по
  срок. Износът по чл. 15/20 е JSON без удостоверения и без чужди лични данни.
- **Изолацията по фирма важи и ИЗВЪН CRUD фабриката.** Всеки маршрут със своя
  логика (смяна на статус, редове по документ, движения, потребители, ТАБЛО,
  ОДИТ, ИМПОРТ) чете с `findFirst`/`where` + `filtroTenant(s)`, не с `findUnique`
  — иначе познат UUID отваря чужд запис. `filtroUtenti(s)` е изключението:
  MASTER е ниво на доставчика и вижда всички фирми. Конфигурация със
  `senzaTenant: true` (само `tenants`) е служебна и трябва да е **MASTER-only**.
- **Номерацията и бизнес-ключовете са ПО ФИРМА** (`@@unique([tenantId, …])`).
  Глобална последователност дава на втората фирма номер след първата: дупки в
  регистъра ѝ и издаден обем на съседа (чл. 21, ал. 2, б. „б" D.P.R. 633/1972).
- **Мобилният вход на техника е QR стикерът.** `src/lib/qr.ts` прави SVG (не
  растер — лепенката се печата), който сочи `/i/<matricola>`, НЕ UUID: матриколата
  е на табелката, прави кода по-рядък и преживява миграция. Адресът идва от
  `APP_URL`, никога от `Host` хедъра — сгрешена база значи стотици преправени
  стикери, затова Compose отказва да стартира без нея. PWA обвивката (манифест,
  `sw.js`, офлайн страница, икони) е ПУБЛИЧНА в middleware-а, иначе приложението
  не се инсталира. Service worker-ът НЕ кешира `/api`: остаряла giacenza изглежда
  като истина. Връщането след вход минава през `ritornoSicuro` — отвореното
  пренасочване се спира на изхода, не на входа.
- **Публичното API е ОТДЕЛЕН слой, не преоблечени вътрешни маршрути.** Ключ
  (SHA-256 отпечатък, показва се веднъж, права по изричен избор — празно значи
  НИЩО), версия В ПЪТЯ (`/api/pubblica/v1/`), изричен `select` на полетата.
  401 = невалиден ключ (непознат/отменен/изтекъл — нарочно неразличими), 403 =
  липсващо право. Webhook доставките се ЗАПИСВАТ в транзакцията на операцията и
  се ПРАЩАТ от автоматизъм (`npm run webhook`): иначе паднал получател проваля
  смяната на статуса, тоест чужд сървър решава дали фактурата ни ще се издаде.
  Подписът покрива `timestamp.corpo` — отметката извън подписа значи преиграване.
  Адресът е HTTPS и публичен (SSRF).
- **Рентабилността е МАРЖ НА ПРИНОСА, не печалба** (`src/lib/redditivita.ts`).
  Косвените разходи не влизат и отговорът си го казва. Липсваща цена е
  НЕИЗВЕСТНА, не нула: нулата прави договора да изглежда печеливш точно когато
  данните липсват. Маржът е спрямо ПРИХОДА, не надценка спрямо разхода.
- **Иконите минават през `src/components/icone.tsx`** (Phosphor, MIT). Никакви
  текстови глифове като икони, никакви емоджита, нищо рисувано на ръка:
  дебелина по роля (regular=навигация · bold=действие · fill=статус), размер
  само от скалата 12/14/16/18, иконата никога не носи смисъл сама.
- **Цветовете на графиките** (8 категорийни, light+dark в `globals.css`) са
  **валидирани** (CVD ΔE≥8, контраст ≥3:1, светлотна алтернация — червено и
  зелено разделени по L). При смяна — превалидирай с dataviz валидатора.
  Цветът следва категорията (каноничен ред в `src/components/Grafico.tsx`), не позицията.

## Архитектура

- `src/lib/crud.ts` + `src/lib/entities.ts` — generic CRUD фабрика: Zod схема +
  конфигурация → пълни REST маршрути. Нова анагрифика = конфиг + 2 тънки route файла.
- `src/lib/voci.ts` — фабрика за редови подресурси (voci/righe) с ricalcola hook.
- `src/components/EntityPage.tsx` — generic списък+форма; страница = конфигурация.
- Dashboard: widget конфигурация per-браузър в `localStorage` (`ea:dashboard:v1`);
  икономическите данни се връщат само за DIREZIONE+ (сървърно).
- `src/lib/query.ts` — разбор на параметрите от URL (страници, UUID, енумерации).
  Сгрешен параметър дава **400 с обяснение**, не 500 от базата.
- Правните и фискалните решения живеят като ЧИСТИ предикати извън маршрутите:
  `regole-fiscali.ts` (преходи, променимост, склад), `retention-logic.ts` (срокове),
  `totals.ts` (пари в цели центесими). Така носят тестове, а не коментари.
- Тестовете са на ТРИ слоя: `npm test` — чистата логика без база (`tsx --test`);
  `npm run test:int` — реален сървър + реална Postgres, изолирана тестова база,
  без мокове (RBAC, преходи, тотали, склад, вход, одит, изолация между фирми);
  `npm run test:e2e` — реален браузър (Playwright), само ПОТОЦИ. Третият слой не
  е излишен: HTTP тестовете минават и при напълно счупен интерфейс — така
  липсващото поле за втория фактор оцеля, а достъпността с клавиатура се оправи
  чак когато E2E-то не можа да кликне връзка, каквато нямаше.

## Тайни

`SESSION_SECRET` и `AUDIT_HMAC_KEY` (мин. 32 знака, различни!) — само на
сървъра, mode 600. Смяната на AUDIT_HMAC_KEY инвалидира старите подписи;
смяната на SESSION_SECRET сваля всички сесии. Никога в репото.
