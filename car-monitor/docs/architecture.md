# Архитектура

Car Monitor следва архитектурата на СИГМА: edge-first, четене директно от D1,
тежката работа е изнесена в прекалкулирани таблици.

## Слоеве

1. **ETL** (`apps/etl` + `packages/ingest`) — адаптери по източник свалят сурови
   обяви, нормализират ги до доменния граф и смятат риск. Cron worker освежава
   скорошен прозорец; голям catchup е CLI-based.
2. **Съхранение** (`packages/db`, D1/SQLite) — нормализирани домейн таблици +
   прекалкулирани rollups + FTS5 индекс.
3. **Четене** (`apps/web`) — React Router v7 SSR worker, чете D1 през
   `@car-monitor/db`. Без отделен API слой — loader-ите четат директно.

## Защо прекалкулирани rollups

Страниците не правят тежки агрегации в реално време. `rollups.sql` пресъздава
`home_totals`, `model_totals`, `seller_totals`, `price_history`, `facet_counts`
и `search_index` след всяко зареждане. Медианите се смятат точно през window
функции.

## Граф и риск

Един и същи автомобил (по VIN/рег. номер) събира множество обяви и събития във
времето. Това позволява проследяване — напр. намаляващ пробег между ГТП отчет и
обява => `mileage_rollback` => `risk_level = red`. Логиката е в
`@car-monitor/shared` (`computeRisk`) и е покрита с тестове.

## Граници на доверие

Публичните данни (обяви) са свободни. Интеграциите с национални регистри (КАТ,
ГТП, застрахователи) имат ограничения за достъп и се третират като production
secrets — точно както СИГМА третира търговския регистър и НАП.
