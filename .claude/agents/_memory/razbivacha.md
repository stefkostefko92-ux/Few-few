- **2026-07-24:** LLM02 Sensitive Information Disclosure (2025) покрива изтичане както от самия модел, така и от приложението около него. За нашите продукти с LLM (mastilko/linketto/Gemini): PII/тайни в prompt-а, в логовете на LLM заявките, или върнати в изхода — всичко е LLM02 повърхност. - **2026-07-24:** OWASP формулира изрично: Prompt Injection (LLM01) НЕ е SQL injection, а Excessive Agency (LLM06) НЕ е broken access control — макар да споделят митигации. Извод за докладване: не мапвай агентна находка към OWASP Web A03/A01 по аналогия; ползвай LLM/ASI таксономията за агенти и Web Top 10 само за продуктовия HTTP слой (два отделни класификатора). _("разграничение LLM vs Web таксономия"; verified; "https://genai.owasp.org/llm-top-10/")_
- **2026-07-24:** Четири канала за запис в агентна памет (таксономия, arxiv 2606.04329): (1) explicit instruction-executed write, (2) system-prompt-driven write, (3) compaction-driven write (при съкращаване на контекст), (4) experience-to-procedure write. Всеки е потенциална врата за отрова. За нашия SubagentStop→_memory хук: покрий и compaction-канала — обобщения/съкращения могат да пренесат отровено съдържание като „поука". _("канали за запис в памет / compaction"; verified; "https://arxiv.org/html/2606.04329v1")_
- **2026-07-24:** MITRE ATLAS отделя AI Attack Staging като тактика — подготвителна работа СПЕЦИФИЧНА за AI атаки: изграждане на proxy/surrogate модели, генериране на adversarial примери офлайн, инфраструктура огледало на целта. Red-team извод: атака срещу наш модел-базиран продукт може да има невидима staging фаза (proxy модел) преди реалния удар — не всичко е видимо в продукционните логове. _("ATLAS ML Attack Staging"; verified; "https://www.vectra.ai/topics/mitre-atlas")_
- **2026-07-24:** ISO/IEC 29147:2018 (Vulnerability disclosure) описва как организацията ПОЛУЧАВА и отговаря на репорти за уязвимости; ISO/IEC 30111:2019 (Vulnerability handling) описва ВЪТРЕШНИТЕ процеси за верификация/анализ/поправка. Двата стандарта заедно очертават фазите на Coordinated Vulnerability Disclosure (CVD). Нашата coordinated-disclosure практика (докладвай насаме + минимална поправка) е съгласувана с тях. _("ISO 29147/30111 CVD стандарти"; verified; "https://www.iso.org/standard/72311.html")_
- **2026-07-24:** Microsoft подчертава: spotlighting е ВЕРОЯТНОСТНА (probabilistic) техника — намалява, но не елиминира риска; затова се комбинира с ДЕТЕРМИНИСТИЧНИ контроли (Purview permissions, блокиране на известни exfil методи, human-in-the-loop). Извод за red-team: не приемай, че делимитер/датамаркинг сам по себе си е достатъчна защита — атакувай през детерминистичния слой (exfil канал). _("probabilistic vs deterministic защита"; verified; "https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks")_
- **2026-07-24:** Microsoft Spotlighting срещу indirect PI — три режима за отличаване на недоверен вход: (1) Delimiting — рандомизиран текст-делимитер преди/след недоверения вход; (2) Datamarking — специални символи, разпръснати из недоверения текст; (3) Encoding — трансформация (напр. base64). Плюс детерминистични контроли: блокиране на markdown-image/link exfil, human-in-the-loop за чувствителни действия. Приложимо при подаване на външно съдържание към нашите агенти. _("spotlighting defense-in-depth"; verified; "https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks")_
- **2026-07-24:** ChatInject (arxiv 2509.22830) заобикаля ограничението, че indirect PI е passive (атакуващият не може да води разговора ход по ход): вгражда СИМУЛИРАНА multi-turn история в един-единствен injection payload, абузирайки chat-template формата. Урок: недоверено съдържание може да фалшифицира „предишни ходове"/системни маркери — валидацията на injection spec трябва да включва payload с фалшиви role-маркери. _("ChatInject chat-template абуз"; verified; "https://arxiv.org/pdf/2509.22830")_
- **2026-07-24:** Crescendo (Microsoft Research, arxiv 2404.01833) — multi-turn jailbreak: започва с невинен въпрос по темата и постепенно ескалира, използвайки СОБСТВЕНИЯ изход на модела за насока; успява обикновено за <5 хода. Експлоатира че повечето safety системи оценяват ОТДЕЛНИЯ ход, не траекторията на разговора. Red-team урок: инжекционните евали не бива да са само single-turn. _("Crescendo multi-turn jailbreak"; verified; "https://arxiv.org/html/2404.01833v1")_
- **2026-07-24:** Prompt injection таксономия: DIRECT = атакуващият е потребителят, слага инструкции директно във входа; INDIRECT = атакуващият вгражда инструкции във външно съдържание (сайт/документ/имейл), консумирано по-късно от модела при взаимодействие жертва↔LLM. Indirect е по-опасен за агенти (файл/уеб/issue = недоверени данни). Мапвай находките си по вектор (direct/indirect) + target система (chat/code-assistant/RAG/agent). _("direct vs indirect PI таксономия"; verified; "https://www.mdpi.com/2078-2489/17/1/54")_
- **2026-07-24:** Prompt-injection защитите дават НЕПЪЛНО покритие срещу memory poisoning: LLM-базирани детектори пропускат ~66% от отровени memory записи (A-MemGuard изследване). Извод за red-team: не разчитай, че „агентът ще разпознае" отровен запис — контролът трябва да е ДЕТЕРМИНИСТИЧЕН (source-required, provenance, schema-валидация), не преценка на модела. _("детерминистичен vs LLM детектор за памет"; verified; "https://arxiv.org/html/2606.04329v1")_
- **2026-07-24:** Memory poisoning се различава фундаментално от prompt injection/jailbreak: изисква само ЕДИН успешен запис, после персистира cross-session (payload-ът не трябва да е в активния контекст всеки път). Изследване: среден ASR ~50%, MINJA атака >95% injection success през обикновени заявки без привилегии. За нашата памет: всеки кандидат-запис е high-stakes — карантината (непроверени НЕ са факт) е правилният fail-closed модел. _("memory poisoning персистентност / MINJA"; verified; "https://arxiv.org/html/2606.04329v1")_
