## Проверени поуки (verified)
- **2026-07-17:** Counter — монотонно растящ брояч (нулира само при рестарт на процеса); питаш го с `rate()`/`increase()`, НИКОГА суровата стойност; за „общ брой събития". _("метрики: counter"; verified; "https://prometheus.io/docs/concepts/metric_types/")_
- **2026-07-17:** Gauge — моментна стойност нагоре/надолу (in-flight заявки, queue depth, температура); агрегираш с `avg`/`max`/`min`/`sum`, не с `rate`. _("метрики: gauge"; verified; "https://prometheus.io/docs/concepts/metric_types/")_
- **2026-07-17:** Histogram — наблюдения в кумулативни кофи (`_bucket{le=...}`) + `_sum` + `_count`; квантилите се смятат СЪРВЪРНО с `histogram_quantile()`, агрегируем между реплики. _("метрики: histogram"; verified; "https://prometheus.io/docs/concepts/metric_types/")_
- **2026-07-17:** Summary — квантили пресметнати в КЛИЕНТА (`{quantile=...}`) + `_sum`+`_count`; НЕ се агрегира между инстанции (не осредняваш квантили) → при няколко реплики предпочитай histogram. _("метрики: summary"; verified; "https://prometheus.io/docs/practices/histograms/")_
- **2026-07-17:** Кардиналност = брой уникални комбинации label стойности; всяка серия яде памет; експлозия при high-card label (`user_id`, `request_id`, `email`) е водеща причина за срив/OOM на Prometheus. _("метрики: кардиналност"; verified; "https://prometheus.io/docs/practices/naming/")_
- **2026-07-17:** OpenMetrics — CNCF стандарт за expositional формат (наследник на Prometheus text format), поддържа exemplars; content-type `application/openmetrics-text`. _("метрики: OpenMetrics"; verified; "https://github.com/OpenObservability/OpenMetrics")_
- **2026-07-17:** Именуване: `<namespace>_<subsystem>_<unit>`, суфикс с базовата единица (`_seconds`, `_bytes`), `_total` за counter; базови единици (секунди, не милисекунди). _("метрики: именуване"; verified; "https://prometheus.io/docs/practices/naming/")_
- **2026-07-17:** Метрика = агрегат, евтина, ниска кардиналност; за high-card детайл (кой точно потребител/заявка) ползвай traces/logs, не нови labels. _("метрики: обхват"; verified; "https://opentelemetry.io/docs/concepts/signals/metrics/")_
- **2026-07-17:** Exemplars прикачат `trace_id` към конкретна histogram кофа — мост метрика→trace („кой request точно седи в P99 опашката"). _("метрики: exemplars"; verified; "https://opentelemetry.io/docs/specs/otel/metrics/data-model/#exemplars")_
- **2026-07-17:** Структуриран лог (JSON с фиксирани полета) > свободен текст: машинно-парсим, филтруем по поле; едно събитие = един ред. _("логове: структура"; verified; "https://opentelemetry.io/docs/concepts/signals/logs/")_
- **2026-07-17:** Нива TRACE<DEBUG<INFO<WARN<ERROR<FATAL; продукция обикновено INFO+; грешно ниво = шум скрива сигнал. _("логове: нива"; verified; "https://opentelemetry.io/docs/specs/otel/logs/data-model/#field-severitynumber")_
- **2026-07-17:** Всеки лог носи `trace_id`+`span_id` (OTel log data model) за корелация лог↔trace — клик от лог към trace и обратно. _("логове: корелация"; verified; "https://opentelemetry.io/docs/specs/otel/logs/data-model/")_
- **2026-07-17:** Семплирай логове при обем (keep 1/N debug), но НИКОГА ERROR/audit — 100% на грешките и одита. _("логове: семплиране"; verified; "https://opentelemetry.io/docs/concepts/signals/logs/")_
- **2026-07-17:** Нула PII/секрети в лог (пароли, токени, PAN, ЕГН, имейл); redaction ПРЕДИ изход; логът е дълготраен → изтичане на данни. _("логове: приватност"; verified; "https://opentelemetry.io/docs/security/")_
- **2026-07-17:** Контекстни полета по резолюция (`service.name`, `env`, `request_id`) като структуриран context, не конкатениран стринг. _("логове: контекст"; verified; "https://opentelemetry.io/docs/concepts/signals/logs/")_
- **2026-07-17:** Span = единица работа (start/end, име, атрибути, статус, събития); trace = дърво от spans с общ `trace_id`. _("traces: span"; verified; "https://opentelemetry.io/docs/concepts/signals/traces/")_
- **2026-07-17:** Parent/child връзка чрез span context (`trace_id`+`span_id`+`trace_flags`); root span няма parent. _("traces: дърво"; verified; "https://opentelemetry.io/docs/concepts/signals/traces/")_
- **2026-07-17:** Context propagation между услуги = W3C Trace Context: HTTP хедъри `traceparent`/`tracestate` пренасят trace през мрежата. _("traces: propagation"; verified; "https://www.w3.org/TR/trace-context/")_
- **2026-07-17:** Baggage (W3C Baggage хедър) пренася key/value по целия trace (напр. `tenant_id`) за cross-cutting контекст; влиза в мрежата → БЕЗ PII/секрети. _("traces: baggage"; verified; "https://www.w3.org/TR/baggage/")_
- **2026-07-17:** Span атрибути по семантични конвенции (`http.request.method`, `url.path`, `db.system`); статус `OK`/`ERROR`; span events за точкови моменти. _("traces: атрибути"; verified; "https://opentelemetry.io/docs/specs/semconv/")_
- **2026-07-17:** Span kinds: SERVER/CLIENT/PRODUCER/CONSUMER/INTERNAL — определят ролята и как се тълкува латентността на span-а. _("traces: span kind"; verified; "https://opentelemetry.io/docs/specs/otel/trace/api/#spankind")_
- **2026-07-17:** Sampling: head-based (реши в началото по `trace_id`, евтино, но може да изпуснеш редки грешки) vs tail-based (реши след пълния trace в Collector — пазиш всички грешни/бавни, но нужен буфер/памет). _("traces: sampling"; verified; "https://opentelemetry.io/docs/concepts/sampling/")_
- **2026-07-17:** `parentbased_traceidratio` дава консистентно решение по `trace_id` — целият trace е или семплиран, или не (без счупени дървета). _("traces: consistent sampling"; verified; "https://opentelemetry.io/docs/languages/js/sampling/")_
- **2026-07-17:** Continuous profiling — постоянно нискоразходно вземане на CPU/heap профили в продукция (pprof/eBPF); четвъртият стълб на наблюдаемостта. _("profiling: същност"; verified; "https://opentelemetry.io/docs/concepts/signals/profiles/")_
- **2026-07-17:** OTel Profiling сигнал — стабилизиран към 2026, pprof-съвместим формат, корелиран с traces (span→flamegraph). _("profiling: OTel статус 2026"; verified; "https://opentelemetry.io/status/")_
- **2026-07-17:** Flamegraph — ширина = време/ресурс на стек рамка; чете се за hot path и регресия между версии. _("profiling: flamegraph"; verified; "https://www.brendangregg.com/flamegraphs.html")_
- **2026-07-17:** OpenTelemetry = CNCF проект (сред най-активните след Kubernetes), vendor-neutral: една инструментация → всеки backend; traces+metrics+logs API/SDK stable, profiles стабилен 2026. _("OTel: обзор 2026"; verified; "https://opentelemetry.io/status/")_
- **2026-07-17:** OTLP — нативният протокол: gRPC порт 4317 / HTTP-protobuf порт 4318; export от SDK/Collector към backend с retry и компресия. _("OTel: OTLP"; verified; "https://opentelemetry.io/docs/specs/otlp/")_
- **2026-07-17:** Collector — pipeline receiver → processor → exporter; отделен процес, разтоварва апа от export логиката. _("OTel: Collector"; verified; "https://opentelemetry.io/docs/collector/")_
- **2026-07-17:** `batch` processor е задължителен за ефективност, `memory_limiter` пази Collector от OOM — сложи и двата в pipeline-а. _("OTel: Collector processors"; verified; "https://opentelemetry.io/docs/collector/configuration/")_
- **2026-07-17:** Топология: agent (sidecar/DaemonSet до апа) + gateway (централен клъстер за tail sampling/агрегация) — двустепенна схема. _("OTel: deployment"; verified; "https://opentelemetry.io/docs/collector/deployment/")_
- **2026-07-17:** Семантични конвенции = стандартни имена на атрибути (`service.name` задължителен, `http.*`, `db.*`, `messaging.*`); еднакви имена = преносими дашборди/аларми между услуги и vendor-и. _("OTel: semconv"; verified; "https://opentelemetry.io/docs/specs/semconv/")_
- **2026-07-17:** `service.name` е задължителен resource атрибут; без него телеметрията е несортируема по услуга. _("OTel: service.name"; verified; "https://opentelemetry.io/docs/specs/semconv/resource/#service")_
- **2026-07-17:** Auto-instrumentation (zero-code: Java agent, Node `--require`, Python `opentelemetry-instrument`) хваща популярни библиотеки; ръчна инструментация за бизнес spans/атрибути. _("OTel: инструментация"; verified; "https://opentelemetry.io/docs/concepts/instrumentation/zero-code/")_
- **2026-07-17:** GenAI семантични конвенции — стандартни атрибути за LLM (`gen_ai.system`, `gen_ai.request.model`, token usage) за AI observability. _("OTel: GenAI semconv"; verified; "https://opentelemetry.io/docs/specs/semconv/gen-ai/")_
- **2026-07-17:** SLI — количествена мярка за качество от гледна точка на ПОТРЕБИТЕЛЯ (добри събития / всички събития: успешни заявки, latency < праг). _("SRE: SLI"; verified; "https://sre.google/sre-book/service-level-objectives/")_
- **2026-07-17:** SLO — целеви праг за SLI за период (напр. 99.9% успешни за 30 дни); вътрешна цел, по-строга от SLA. _("SRE: SLO"; verified; "https://sre.google/sre-book/service-level-objectives/")_
- **2026-07-17:** SLA — външен ДОГОВОР с последици (компенсация) при пропуск; SLO без последици е вътрешен; SLA обикновено по-хлабав от SLO. _("SRE: SLA vs SLO"; verified; "https://sre.google/sre-book/service-level-objectives/")_
- **2026-07-17:** Error budget = (1 − SLO) × общо събития; 99.9% SLO → 0.1% бюджет ≈ 43 min надолнина/30 дни; бюджетът се харчи за иновация/риск. _("SRE: error budget"; verified; "https://sre.google/sre-book/embracing-risk/")_
- **2026-07-17:** Error budget policy — при изчерпан бюджет: feature freeze, само надеждностни промени докато не се възстанови; договорено ПРЕДВАРИТЕЛНО между dev и SRE. _("SRE: EB policy"; verified; "https://sre.google/workbook/error-budget-policy/")_
- **2026-07-17:** „100% е грешна цел за надеждност" — почти винаги; закова цена без стойност; целѝ достатъчно, за да е потребителят доволен. _("SRE: надеждностна цел"; verified; "https://sre.google/sre-book/embracing-risk/")_
- **2026-07-17:** Четири златни сигнала: latency, traffic, errors, saturation — минимумът за user-facing система. _("SRE: златни сигнали"; verified; "https://sre.google/sre-book/monitoring-distributed-systems/")_
- **2026-07-17:** RED метод за request-driven услуги: Rate (заявки/с), Errors (провалили/с), Duration (латентност) — на всяка услуга. _("SRE: RED"; verified; "RED метод — Tom Wilkie / Weaveworks, „Monitoring Microservices"")_
- **2026-07-17:** USE метод за ресурси: Utilization, Saturation, Errors — на всеки ресурс (CPU, памет, диск, мрежа). _("SRE: USE"; verified; "https://www.brendangregg.com/usemethod.html")_
- **2026-07-17:** Прозорец на SLO: rolling (30 дни назад, плавен) vs calendar (месец, нулира се); rolling е по-щадящ към единичен инцидент. _("SRE: SLO прозорец"; verified; "https://sre.google/workbook/implementing-slos/")_
- **2026-07-17:** Аларма по СИМПТОМ (потребителят боли: висок error rate/латентност), не по ПРИЧИНА (CPU 90%); причината е за диагностика в дашборд, не за page. _("аларми: симптом"; verified; "https://sre.google/sre-book/monitoring-distributed-systems/")_
- **2026-07-17:** Multi-window multi-burn-rate (SRE Workbook) комбинира бърз + бавен прозорец → лови и остри спайкове, и бавен дрейф с малко фалшиви аларми. _("аларми: MWMBR"; verified; "https://sre.google/workbook/alerting-on-slos/")_
- **2026-07-17:** Burn rate = скорост на харчене на error budget спрямо равномерна; burn rate 1 = харчиш точно за целия период; >1 = ще изчерпаш по-рано. _("аларми: burn rate"; verified; "https://sre.google/workbook/alerting-on-slos/")_
- **2026-07-17:** Стандартни прагове (SRE Workbook, 30д бюджет): 14.4× за 1h (2% бюджет) → page; 6× за 6h (5%) → page; 1× за 3d (10%) → ticket. _("аларми: burn-rate прагове"; verified; "https://sre.google/workbook/alerting-on-slos/")_
- **2026-07-17:** Всяка page аларма е ACTIONABLE и спешна — изисква човешко действие сега; иначе е ticket/дашборд, не page. _("аларми: actionable"; verified; "https://sre.google/sre-book/monitoring-distributed-systems/")_
- **2026-07-17:** Alert fatigue — много/шумни аларми притъпяват реакцията; изтрий неактивните, групирай, вдигни праговете; всяка аларма да „струва" прекъсване. _("аларми: fatigue"; verified; "https://sre.google/sre-book/monitoring-distributed-systems/")_
- **2026-07-17:** Alertmanager: групиране (`group_by`), заглушаване (`silence`), потискане (`inhibit_rule`), маршрутно дърво (`route`) към receiver-и; HA двойка се дедупира автоматично. _("аларми: Alertmanager"; verified; "https://prometheus.io/docs/alerting/latest/alertmanager/")_
- **2026-07-17:** `for:` в alerting rule изисква условието да е вярно N време (pending→firing) — гаси flapping. _("аларми: for"; verified; "https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/")_
- **2026-07-17:** Inhibition — потисни зависимите аларми (целият клъстер down → не пращай 100 per-instance аларми), прати само кореновата. _("аларми: inhibition"; verified; "https://prometheus.io/docs/alerting/latest/configuration/")_
- **2026-07-17:** Prometheus е pull модел: сам scrape-ва `/metrics` endpoint на targets на `scrape_interval`; service discovery намира targets. _("prometheus: pull"; verified; "https://prometheus.io/docs/introduction/overview/")_
- **2026-07-17:** `rate(counter[5m])` — среден per-секунда ръст за прозореца, устойчив на нулиране на counter; за alerting/дашборд. _("promql: rate"; verified; "https://prometheus.io/docs/prometheus/latest/querying/functions/#rate")_
- **2026-07-17:** `irate()` — моментен ръст от последните 2 точки; за бързо-променливи графики, шумен за аларми → предпочитай `rate()`. _("promql: irate"; verified; "https://prometheus.io/docs/prometheus/latest/querying/functions/#irate")_

- **2026-07-17:** Recording rules предпресмятат скъпи изрази в нови серии на интервал → ускоряват дашборди/аларми; именувай `level:metric:operation`. _("promql: recording rules"; verified; "https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/")_
- **2026-07-17:** Контрол на кардиналност: `metric_relabel_configs` дропва high-card labels/серии на scrape; `sample_limit` таван; никога `user_id` като label. _("prometheus: cardinality контрол"; verified; "https://prometheus.io/docs/prometheus/latest/configuration/configuration/#metric_relabel_configs")_

- **2026-07-17:** Loki — лог агрегация „като Prometheus за логове": индексира само labels, не пълния текст → евтино; заявки с LogQL. _("logs backend: Loki"; verified; "https://grafana.com/docs/loki/latest/get-started/")_
