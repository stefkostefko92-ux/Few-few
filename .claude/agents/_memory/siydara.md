## Проверени поуки (verified)
- **2026-07-06:** relationLoadStrategy (preview relationJoins): 'join' дефолт (LATERAL JOIN, единична заявка) vs 'query' (много заявки, app-level join). - **2026-07-06:** Connection pool дефолт: Prisma 6 = num_physical_cpus*2+1; Prisma 7 (driver adapters) = фиксирано 10. pool_timeout дефолт 10s. Необуздан Promise.all в seed над pool size опашкова и над timeout гърми — предпочети sequential/ограничен concurrency. _("паралелен vs sequential seed, connection pool изчерпване"; verified; "https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool")_
- **2026-07-06:** Interactive $transaction дефолти: timeout 5000ms, maxWait 2000ms. Голям seed в една транзакция гърми на timeout — за големи датасети chunk-вай отделни createMany вместо една дълга транзакция; настрой {timeout, maxWait} при нужда. _("batching на голям seed датасет с транзакции"; verified; "https://www.prisma.io/docs/orm/prisma-client/queries/transactions")_
- **2026-07-06:** Seed data трябва в dependency ред: parent преди child, иначе Prisma гърми при създаване на relation към несъществуващ запис. _("ред на upsert-ите при свързани модели"; verified; "https://www.prisma.io/docs/orm/prisma-migrate/workflows/seeding")_
- **2026-07-06:** relationMode='prisma' НЕ създава автоматично FK индекси (нужни ръчни @@index) и носи performance разход чрез емулация в клиента; 'foreignKeys' е default за релационни БД. Провери коя мода е в schema.prisma преди да разчиташ на DB-level FK при seed ordering. _("seed dependency ordering + FK integrity"; verified; "https://www.prisma.io/docs/orm/prisma-schema/data-model/relations/relation-mode")_

За единичен последователен seed скрипт това НЕ важи — retry е излишен. _("разбиране кога upsert е безопасен в seed (единичен процес)"; verified; "https://github.com/prisma/prisma/issues/3242")_
