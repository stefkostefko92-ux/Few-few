## Карантина (непроверено — хипотези, никога не се четат като факт)
- **2026-07-23:** SQLite WAL + synchronous=NORMAL преживява крах на ПРОЦЕСА (комитната tx оцелява); загуба на ТОК иска synchronous=FULL. Write-ahead моделът зависи от await-нат durable commit преди всеки външен I/O. _("офлайн durability"; probable; "SQLite durability модел; допускане — не проверено срещу текущите PRAGMA на CSPos")_
- **2026-07-23:** Schema има Sale.status String @default('COMPLETED') (schema.prisma:199) и Sale.number/unp @unique (:197-198) — достатъчно за PENDING write-ahead + идемпотентен commit чрез CAS updateMany(where status=PENDING). Липсва маркер 'печат в полет' — предлагам Sale.fiscalStartedAt. _("CSPos схема"; unverified; "CSPos/prisma/schema.prisma:194-234 (прочетено)")_
- **2026-07-22:** Печат към ФУ е външен I/O и НЕ може да е вътре в SQLite транзакция — dual-write. Правилен ред: write-ahead PENDING+УНП преди печат → печат → идемпотентен commit ключиран по номер бон/УНП → reconcile при старт. Формулировката 'бон и запис в една транзакция' е технически невъзможна за хардуерен принтер. _("POS архитектура / крах-възстановяване"; unverified; "инженерна практика (write-ahead + идемпотентен ключ срещу non-transactional resource); домейнов извод за offline-first Electron каса")_
