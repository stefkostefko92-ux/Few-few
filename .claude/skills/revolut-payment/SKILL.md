# Revolut предпазители (Merchant и Business)

Собственик = агентът **Продавача**. Наследява инвариантите на `stripe-payment` (сумата от сървъра, права само
след проверено събитие, идемпотентност, тайни на сървъра, цели центове без float). Тук е само специфичното за
Revolut. Справките с източници: Merchant — [`references/spravka.md`](references/spravka.md) (API 2026-09-22),
Business — [`references/business.md`](references/business.md) (API 1.0); и двете свалени 2026-11-17. Паричен
код = ядро → тест първо, ревю от Кодаджията.

Merchant и Business са **два отделни API**: различен хост, ключ, уебхук, тайна и парсер. Не ги смесвай.

## Непреодолими инварианти — Merchant API

1. **Правата идват само след `GET /api/orders/{id}`**: `state: completed` + точна сума + валута + нашият
   `merchant_order_data.reference`. Уебхукът и redirect-ът са само сигнал. Тялото на уебхука няма сума и
   няма id на събитие, а редът на събитията не е гарантиран.
2. **Подписът на уебхука се проверява върху суровото тяло** със `signing_secret` и с допуск по времето.
   Невалиден подпис → отказ. Схемата `v1=<hex>` над `v1.{timestamp}.{тяло}` не е сверена с ръководството
   (днес 403), затова промяна по нея минава само след проба с истински уебхук в sandbox.
3. **Дедупликация по `event` + `order_id`** с условен запис (няма id на събитие). Плюс **проверка на
   висящите** по reference (reconciler): изгубен уебхук не бива да оставя платена поръчка без права.
4. **Отговорът на уебхука:** 2xx (препоръчано 204) само при успех. Вътрешна грешка → **4XX** (409), не 5XX.
   Повторен опит Revolut прави само при 4XX или timeout (3 пъти през 10 мин.), а 200–399 е потвърждение.
   Не разчитай на повторна доставка след 2xx.
5. **Create order няма `Idempotency-Key`.** При timeout първо търси поръчката по reference, после нов опит.
   Refund — `Idempotency-Key` = нашият id на refund-а.
6. **Refund е нова поръчка `type: refund`** (`related_order_id`), до 2 дни до краен статус. Приключва се по
   `state` на поръчката **и** по `payments[].state`: `declined`/`failed` = неуспех. От 2026-09-22 отказан
   refund през Revolut Pay връща **200**, не 400. Кодът трябва да хваща и двата пътя.
7. **Спорове `DISPUTE_*`:** тялото носи само `dispute_id` → `GET /api/disputes/{id}` (само Production) → запис
   и известие до администратора със срока за отговор. **Без автоматично отнемане** — решава човек. Модел:
   `rilievi/src/pagamenti/contestazioni.ts`. Уебхукът се абонира за `DISPUTE_*` с fallback само към
   поръчките при 400/422.
8. **`customer` само с `id`.** Само имейл/телефон/име създава нов клиент в Revolut на всяка поръчка.
9. **Версията (`Revolut-Api-Version`) се сменя само по разликата** между `merchant.yaml` на двете версии +
   тест за всяка разлика. Без хедър на ендпойнт, където е по избор, важи **най-ранната** версия.
10. **Sandbox по подразбиране, Production само изрично.** Subscriptions, usages и disputes съществуват само в
    Production → тестове с фикстури от примерите в спецификацията (напр. `Res-Refund-Declined`).
11. **Тайни:** secret key и `signing_secret` само на сървъра (mode 600). `signing_secret` се връща във всеки
    GET на уебхука — не го логвай и не го връщай към клиента. Ключ с подписани заявки (Ed25519) в Production
    иска `Revolut-Api-Timestamp` (Unix ms) + `Revolut-Api-Signature` (Base64) над `timestamp + МЕТОД + път от
    /api + query без „?“ + минифицирано тяло`, без разделители (сверено с примерите на Revolut, 17.11.2026 —
    `references/business.md` § 2); без поддръжка → fail-closed.
12. **Payouts** са само към собствената Business сметка и за целия баланс; **disbursements** и проверка на
    карта са само за MCC 7995. Не са инструмент за изплащане към трети лица.

## Непреодолими инварианти — Business API (`b2b.revolut.com`)

Днес никой продукт не го вика. Тези правила важат от първия ред код с него.

1. **Ключът по подразбиране е само за четене** (`accounts:read`, `transactions:read`). Права за `/pay`,
   `/transfer`, payout links и обмяна — само с изрично решение на собственика. Пари навън излизат като
   **payment draft**, който човек изпраща от приложението Revolut Business (през API такъв ендпойнт няма).
2. **API ключ, не OAuth.** OAuth с JWT client assertion е остарял (`business.yaml` ред 14467) — нов код не се
   строи върху него. Частният ключ Ed25519 се генерира локално, стои само на сървъра (mode 600), отделен за
   Sandbox и Production, с IP allowlist; смяна на около 90 дни, при компрометиране — веднага.
3. **Сумите са `double` в основни единици** (евро, не центове). Превръщане към цели центове с десетичен разбор
   на низа, никога с float аритметика; сравнява се с нашите `amountCents`.
4. **`request_id` = нашият id**, записан ПРЕДИ заявката. Важи само 2 седмици. Повторен → 400 `code: 3020`, а
   не първата транзакция: тогава търси с `GET /transactions?request_id=…&from=…` (прозорец ≤ 14 дни), не прави нов.
5. **Уебхукът е сигнал, правата са след GET.** Уебхуците v2 са на `/api/2.0` (`TransactionCreated`,
   `TransactionStateChanged`, `PayoutLink*`). Правата и записите тръгват само след
   `GET /transaction/{id}`: `state: completed`, кредитен leg, валута, сума и нашето основание. Дедупликация по
   `event` + `data.id` + състояние (id на събитие няма). Изгубените се хващат с `/transactions` по прозорец и
   `/failed-events` (до 21 дни назад).
6. **Подписът на Business уебхука е НЕПРОЧЕТЕН** (ръководството връща 403). Не приемай, че е като при
   Merchant: преди кода — проба с истински уебхук в Sandbox и запис на схемата в справката.
7. **Страниците на `/transactions` се четат със застъпване** (keyset по `created_at`, `to` е изключителен) и
   повторенията се махат по `id`.
8. **Банковите сметки на клиентите на живо** (AIS по PSD2) = чужди банкови данни при нас → първо Правния
   Разбирач. Дотогава остава вносът от файл (camt.053).

## Грешки (симптом → причина → поправка)

| Симптом | Причина | Поправка |
|---|---|---|
| Платено, а планът не е даден | изгубен уебхук или 2xx при грешка | 4XX при грешка + проверка на висящите по reference |
| Refund стои „в ход“ дни наред | гледа се само `order.state` | приключвай и по `payments[].state` |
| 404 на `/api/webhooks` или `/api/customers` | версия под 2024-09-01 | вдигни версията по разликата в спецификацията |
| Нови клиенти в Revolut на всяка поръчка | `customer` без `id` | махни `customer` или пази `customer.id` |
| 400 „invalid version“ | липсва задължителен хедър | `Revolut-Api-Version` на всяка заявка |
| Business: сумата е 100 пъти различна | `double` в евро, сравнено с центове | десетичен разбор към цели центове |
| Business: 400 `code: 3020` при повторен опит | `request_id` вече е ползван | намери транзакцията по `request_id`, не прави нова |
| Business: двойно плащане след седмици | `request_id` е по-стар от 2 седмици | първо търси по `request_id`, после нов опит |
| Business: 401 `code: 1000` | изтекъл OAuth токен (остарял вход) | мини на API ключ |

## Дефиниция на „готово"

Права само след GET (`completed` + сума + валута + reference) · подпис върху суровото тяло · дедупликация +
проверка на висящите · 4XX при вътрешна грешка · refund приключва и по `payments[].state` · споровете стигат до
човек · версия по спецификацията · тайни на сървъра · тест първо. За Business още: ключ само за четене ·
изходящо плащане само като чернова, изпратена от човек · суми към центове с десетичен разбор · `request_id`
записан преди заявката. Договорът и правото около плащанията → Правния Разбирач; данъците → Данъчника.
„Не е правен съвет".
