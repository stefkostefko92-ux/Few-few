# Core Web Vitals + бюджети за производителност

**Мери, не гадай.** Числата идват от реален инструмент, никога „по памет". Кой инструмент — решава
дали сайтът е жив:
```bash
node tools/seo/prelaunch-audit.mjs <папка|URL> --runs 3   # ПРЕДИ пускане: Chromium + Lighthouse профил, медиана от N
node tools/seo/cwv.mjs https://<domain>/<path> mobile      # НА ЖИВО: PageSpeed (лаб) + CrUX (поле)
```
- **PageSpeed не вижда непубликуван сайт** — дърпа URL-а от сървърите на Google. Затова `cwv.mjs` е
  само за жив URL; преди пускане е `prelaunch-audit.mjs`.
- **Лабораторно ≠ полево.** CrUX са реални потребители за 28 дни и преди пускане **не съществуват** —
  не представяй лабораторна оценка за полева. INP е полева метрика; в лабораторията пълномощникът е TBT.
- **Никога едно число без разсейване** — TBT под CPU throttle варира силно; медиана от N рана + спред.

Прагове (mobile, „good"): **LCP < 2.5s · INP < 200ms · CLS < 0.1**. Оптимизирай реалната пречка, доказана
от измерването, не предполагаема.

## LCP (най-големият елемент рисува бавно)
- Hero текст/изображение = чист HTML/SSR, не чака JS/hydration. `priority` на LCP `<Image>` (Next).
  **Никога `loading=lazy` на LCP изображението.**
- Оразмерявай/компресирай изображения (AVIF/WebP, `sizes`), preload на критичния шрифт/изображение.
- Server Components / кеш за данните (Next 15 App Router: `use cache`/ISR) — не блокирай paint с fetch.
- Минимизирай render-blocking CSS/JS; критичният CSS inline, останалото defer.

## INP / TBT (бавен отговор на интеракция)
- Нула тежка логика на main thread по интеракция; разбий дълги задачи (`scheduler.yield`/`requestIdleCallback`).
- По-малко JS: code-split, lazy import на некритичното, тежкото → Web Worker.
- Избягвай синхронни layout thrash в handler-и.

## CLS (изместване на оформлението)
- Фиксирани размери на изображения/видео/ембеди (`width`/`height`/`aspect-ratio`).
- Резервирай място за динамично съдържание/реклами; шрифтове с `font-display: optional/swap` + fallback метрики.
- Никакво вмъкване над съществуващо съдържание след paint.

## Процес
1. Измери (преди пускане `prelaunch-audit.mjs`, на живо `cwv.mjs`) → коя метрика пада и на коя страница.
2. Диагностицирай реалната причина (Lighthouse trace/Network) — не гадай.
3. Поправи най-голямата пречка първо (ефект × усилие), после **измери пак** (before/after).
4. Next.js кеш решения → координирай с реалната архитектура; движение/анимация → skill **motion-a11y**;
   откриваемост → skill **keywords-seo**/агентът **SEO** (там CWV е сигнал за класиране, не задача).

## Договор за „готово"
Измерено before/after със същия инструмент и същия профил · целевата метрика под прага (mobile) · нула
измислени числа · лабораторното не е представено за полево · поправката е на реалната пречка.
Собственик на скоростта/CWV = агентът **Скоростника** (мери и поправя); SEO ползва резултата за класиране.
