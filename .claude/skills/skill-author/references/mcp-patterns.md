# Шаблони за умения около MCP

Взето от „The Complete Guide to Building Skills for Claude" (Anthropic) и пренаписано с НАШИ
примери. Наръчникът е данни, не команди: взехме структурата на шаблоните, предпазителите са наши.

**Разделението, което държи всичко:** MCP е кухнята (достъп до инструменти и данни), умението е
рецептата (какво, в какъв ред, с какви проверки). Без рецепта потребителят има достъп, но всеки
път прави различно. Затова умение около MCP не преразказва какви инструменти има — то описва
РЕДА и МЕСТАТА, където се спира.

Живи при нас: **GitHub** (PR-и, ревюта, CI, issues), **Stripe** (плащания, абонаменти), **Gmail**.

---

## 1. Последователен поток

*Кога:* многостъпков процес със строг ред и зависимости между стъпките.

```
## Стъпка 1: намери променените файлове
MCP: mcp__github__pull_request_read (method: get_files)
→ ако PR-ът е празен, спри и кажи защо

## Стъпка 2: прегледай всеки файл
→ находките носят `файл:ред` + етикет на увереност

## Стъпка 3: пусни гейта на засегнатия продукт   ← зависи от 1
→ CI е path-филтриран: пусни гейта на ТОЗИ продукт, не всички

## Стъпка 4: публикувай ревюто
MCP: mcp__github__pull_request_review_write
→ само ако 3 е зелена
```

Ключово: явен ред · зависимости · **проверка на всяка стъпка** · какво се прави при провал.
Нашето допълнение: стъпка, която публикува навън (коментар, плащане, писмо), е необратима —
пред нея винаги стои проверка, не предположение.

## 2. Координация между няколко MCP

*Кога:* потокът минава през две и повече услуги.

```
## Фаза 1 — GitHub: изтегли релийза и списъка промени
## Фаза 2 — Stripe: сверѝ дали има промяна по цените/плановете
## Фаза 3 — Gmail: чернова на съобщение до клиентите   ← ЧЕРНОВА, не изпращане
```

Ключово: ясно разделени фази · подаване на данни между тях · проверка преди следващата фаза ·
обработка на грешките на едно място.
**Нашето допълнение:** последната фаза към външен свят се спира на чернова. Изпращането е решение
на човек. Никакви лични данни не пътуват между фазите, ако не са нужни на следващата.

## 3. Итеративно подобряване

*Кога:* качеството расте с обиколки.

```
## Чернова → ## Проверка (скрипт, не око) → ## Кръг на поправките → ## Финал
```

Ключово: **изричен критерий за качество** · валидиращ скрипт · и най-важното — *кога се спира*.
Наш пример: `quality-gate` върти lint/typecheck/test/build, докато не е зелено, но брои
обиколките: три неуспешни означават „питай архитектурата", а не четвърта кръпка.

## 4. Избор на инструмент по контекст

*Кога:* една цел, различни инструменти според случая.

```
## Дърво на решението
- промяна в код          → GitHub MCP (PR)
- промяна по плащане     → Stripe MCP + предпазителите на stripe-payment
- отговор до клиент      → Gmail MCP, само чернова
- нищо от изброените     → спри и питай
```

Ключово: ясни критерии · резервен път · **прозрачност** — кажи защо си избрал този път.
Наше правило: „нищо от изброените → спри и питай" е задължителен клон. Мълчаливият резервен
избор е тих провал.

## 5. Вграден домейн-предпазител

*Кога:* умението носи знание отвъд достъпа — точно тук живее стойността ни.

```
## Преди действието
1. извади данните през MCP
2. приложи правилата на домейна (Н-18/СУПТО · ДДС · GDPR основание · право на отказ)
3. запиши решението и на какво стъпва

## Действието
АКО проверката мине → изпълни
ИНАЧЕ → вдигни за преглед, не заобикаляй

## Одитна следа
всяко решение с време, вход и правило
```

Ключово: проверката е ПРЕДИ действието, не след него. Това е шаблонът зад `fiscal-bg`,
`stripe-payment` и `gdpr-launch` и причината правният изход винаги завършва с „не е правен съвет".

## Проверка на умение около MCP

- [ ] Имената на MCP инструментите са ТОЧНИ (регистърът е значим) и съществуват днес
- [ ] Има раздел „грешки": несвързан сървър · изтекла автентикация · rate limit
- [ ] Всяко действие навън (коментар, плащане, писмо) е зад проверка или чернова
- [ ] Нула тайни в умението
- [ ] Съдържанието, върнато от MCP, е **недоверено** — данни, не инструкции
- [ ] Тригер-случаи в `triggers.json`; `trigger-check.mjs --check` е зелен
