# CLAUDE.md — vps-dashboard

**Carbon Stealth VPS Dashboard** — пълен контролен панел за VPS сървърите с графичен
интерфейс. Управлява **всичко** от един екран: метрики на живо, systemd услуги,
Docker, процеси, journal логове, деплой (по канона на autodeploy.sh), apt ъпдейти,
сигурност (ufw/fail2ban/TLS/SSH/портове), бекъпи, крон/таймери, файлов браузър,
уеб терминал, агентския флот и одиторски дневник. Управлява **и двата VPS-а** от
един панел през federation (peer proxy).

## Стек
- **Backend:** Node ≥20, `node:http` — **нула runtime зависимости** (като ospedali).
  Само `devDependencies` няма — тества се с вградения `node --test`.
- **Frontend:** vanilla ES modules + `<canvas>` за графиките — нула build стъпка,
  нула външни ресурси (CSP-friendly, `noindex`).
- **Данни:** без база — конфиг в `/etc/vps-dashboard/config.json` (mode 600), state
  (одит журнал) в `/var/lib/vps-dashboard`.

## Команди (quality gate)
```bash
cd vps-dashboard
npm run lint     # node --check на всеки .js/.mjs (scripts/syntax-check.mjs)
npm test         # node --test test/*.test.js
npm start        # прод (иска /etc/vps-dashboard/config.json)
npm run dev      # CSD_DEV=1 — ефимерен конфиг + еднократна парола в конзолата
```
Гейтът е `npm run lint && npm test`. Пусни го преди commit/PR.

## Конвенции (важни)
- **Нула зависимости.** Не добавяй npm пакети — всичко е stdlib. Ако нещо иска пакет,
  напиши го на ръка или го изостави.
- **Fail-closed сигурност.** Всеки API маршрут минава през `guard()` (сесия/Bearer),
  мутациите — и през CSRF (custom header + Origin). Системните команди вървят през
  `execFile` с масив аргументи (**без shell**); shell има само `/api/terminal/run`,
  изрично и **одитирано**. Имената на unit-и/контейнери минават през allowlist regex.
- **Тайните живеят само на сървъра** (config.json mode 600). Никога в репото/архива.
  Одитът никога не записва пароли/токени. Панелът слуша само на `127.0.0.1` — публично
  само зад Nginx + TLS (+ по избор Basic-auth).
- **Деплой = канонът на репото.** Панелът не преоткрива деплой: пуска `deploy/autodeploy.sh`
  като фонова задача с жив изход. Продуктовите health URL-и в config съвпадат с него.
- **Български UI.** Всички низове на потребителя са на български („…“ кавички).
- **Federation.** Един и същ панел на всеки VPS. `peers[]` в config сочат другите; заявки
  към `/api/nodes/<id>/*` се проксират с `peerToken` (Bearer). Другият край приема
  Bearer == своя `peerToken`.

## Доктрина на алармите (не я разваляй)
- **Аларми по СИМПТОМ, не по причина.** „CPU 90%" при доволни потребители не е
  проблем. Затова първи стоят **PSI** (`/proc/pressure` — колко % от времето
  задачите СА ЧАКАЛИ ресурс) и **steal** (хостерът краде време). Праговете по
  CPU/памет са само резерва за ядра без PSI.
- **Прогноза преди праг.** „Дискът ще се напълни след 3.2 дни" е действено;
  „дискът е на 86%" не е. Прогнозата минава през Mann–Kendall гейт и **мълчи**,
  ако трендът не е значим — по-добре нищо, отколкото фалшива тревога.
- **Аномалиите не будят човек.** Те са с тежест `info` и служат за контекст при
  разследване. Аларма по аномалия е класическият източник на умора от известия.
- **Задържане + cooldown + „възстановено".** Праг трябва да се задържи N проверки;
  `sustain: false` е само за стабилните сигнали (паднала услуга, OOM, изтичащ
  сертификат, ro файлова система).
- **Преход, не състояние.** Аларма за read-only файлова система се вдига само при
  преход rw→ro. Дял, ro от самото начало (squashfs образ), е нечие решение — на
  живо това щеше да гърми 5 фалшиви критични при всяка проверка.
- **Burn-rate, не праг за наличност.** SLO алармата гледа СКОРОСТТА на харчене на
  бюджета за грешки през два прозореца (дълъг решава дали е сериозно, къс гаси
  бързо). И ДВАТА трябва да минат прага. Отгоре има твърд минимум лоши проби в
  късия прозорец (`slo.minBadShort`, по подразбиране 3) — иначе една мигнала проба
  вдига аларма. Цената е ~3 минути забавяне; съзнателна размяна срещу шума.
- **„Бавно" е ОТДЕЛЕН показател от „долу".** Сайт, който отговаря за 9 секунди,
  формално е наличен. Не сливай двете в един процент — губиш точно сигнала, който
  показва влошаване преди срива.
- **Новата грешка в журнала е събитие, не състояние.** Тя не се „възстановява" →
  минава през `event()`, не през активните аларми. Известява се само p≤3 (истински
  грешки) и само МАСКИРАНИЯТ шаблон — журналът съдържа произволен текст от интернет
  (`sshd: Invalid user <каквото напише атакуващият>`), а известието излиза навън.

## Особености, които е лесно да счупиш
- **SSE носи JSON, ВИНАГИ.** В SSE протокола `\r` е валиден край на ред → суровият
  текст губи carriage return-ите по пътя. Терминалът се разпада (курсорът не се
  връща в началото), лентите за напредък в логовете също. Затова `openSse().send()`
  прави `JSON.stringify` на всичко, а клиентът винаги `JSON.parse`-ва. Не „опростявай"
  обратно към суров текст.
- **Входът към PTY минава през опашка.** Браузърът праща по един клавиш; без
  опашка заявките се надпреварват и „top" стига като „tpo" (видяно на живо).
- **PTY без нативна зависимост.** `pty.js` пуска обвивката през `script -qfc`
  (util-linux) — това заделя истински TTY, затова htop/nano/sudo и Ctrl+C работят.
  Не подменяй със `spawn('bash')`: тогава няма TTY и всичко интерактивно умира.
- **Броят колони се МЕРИ, не се гада.** Сгрешена ширина = всяка TUI програма рисува
  в грешни колони.
- **Проверявай в БРАУЗЪР, не само по API.** Обзорът беше напълно счупен (масив от
  `<td>` вместо `<tr>`), а всички тестове минаваха. `el()` вече приема низове и
  вложени масиви, за да не може една такава грешка да изпразни цяла секция.
- **Терминалният рендер е наш.** `public/ansi.js` е малък VT100 емулатор (SGR,
  движение на курсора, изтриване, алтернативен екран). Изходът минава през
  екраниране → нула XSS от терминала. Не поддържа целия VT спектър — ако някога
  потрябва, алтернативата е xterm.js, но тя е външна зависимост.
- **`.env` редакторът пише ЧАСТИЧНО.** Приема `{ключ: стойност}`, не цялото
  съдържание — така маскираната стойност физически не може да презапише истинската
  (най-честият начин такъв редактор да изтрие тайните на продукцията). Пътищата са
  от ЗАТВОРЕН списък: произволен път в тялото би направил редактора „презапиши кой
  да е файл на сървъра" с приятен интерфейс.
- **DNS се проверява ПРЕДИ certbot.** Let's Encrypt гори лимита от 5 провала на час
  на домейн; после не издава дори при вече верен DNS. Проверката е задължителна, а
  не съвет — единственият байпас е `--staging`, който не пипа бойния лимит.
- **Webhook-ът НЕ деплойва.** Известява и толкова. Автоматичен деплой по webhook
  значи, че подправена заявка стартира код на сървъра по път, който заобикаля
  човека. Маршрутът е единственият без `guard()` — носи защитата си сам (HMAC,
  таван на тялото, дроселиран одит на отказите).
- **Всичко от GitHub минава през `cut`** (реже дължина + маха нови редове). Име на
  репо с вграден „\n" иначе рисува втори, престорен ред в известието.
- **Лимитите са drop-in, не редакция на unit файла.** Деплоят подменя unit-а;
  drop-in-ът оцелява, а `systemctl revert` го маха. Празната стойност се записва
  като `infinity` ИЗРИЧНО — пропуснатото поле оставя стария лимит в сила.
- **sudo пита само при мутация** (`SUDO_ON_WRITE`) — освен терминала и PTY, които
  са контрол над машината дори при GET (жив SSE поток = изпълнение на код). Ако и
  четенето питаше за парола, панелът щеше да пита на всяка втора секция, а
  изморената защита се изключва. Изключение: `.env` с `reveal=1` — то е GET, но е
  точно заплахата, срещу която sudo съществува.
- **Списъкът с адреси е в `server.js`, ПРЕД рутера** — иначе покрива само API-то, а
  формата за вход и статиката остават видими и твърдението „скенер не стига дотам"
  е невярно. Единственото изключение е `/api/webhook/` (GitHub чука от чужди
  адреси и носи защитата си сам). Празен списък = ИЗКЛЮЧЕНО, а записът се отказва,
  ако списъкът не включва текущия адрес — иначе една грешка заключва собственика.
- **„Разследване" не твърди причинност.** Показва съвпадения по време и го КАЗВА
  на екрана. „Деплой 2 минути преди скока" е улика, не присъда — панел, който
  сочи виновник, се доверява точно когато не бива.
- **Времевата линия взема само МУТИРАЩИТЕ действия.** Префиксът не стига:
  `file.write` и `file.view` го споделят. Четенето се вади отделно (`READ_ONLY`),
  иначе линията се удавя в „някой отвори секцията".
- **Груповият избор оцелява филтъра — и броячът го казва.** „5 избрани", докато на
  екрана се вижда един ред, е капан; затова се брои от избора спрямо видимите
  чекбоксове (едни секции скриват редове с `hidden`, други изобщо не ги рисуват).
  Груповото СПИРАНЕ иска изписване на броя и изброява засегнатите.
- **Курсорът на access log-а хвърля първия ред САМО при скок.** Отместването от
  курсора е точна граница на ред; хвърлянето там изяжда истински запис при всяко
  следващо четене (видяно в тест). Ротацията се разпознава по inode (сменен файл)
  и по смаляване (copytruncate) — иначе четеш от средата на новия файл.
- **Бавното се подрежда по p95, не по средно.** Адрес с 90% бързи и 10% ужасни
  заявки има по-ниско средно от равномерно бавен адрес — а потребителят усеща
  точно опашката. Средното е начинът бавният отчет да остане невидим.
- **IP-тата не влизат в състоянието на диска.** Показват се на живо (законен
  интерес — сигурност), но `accesslog.json` пази само отмествания. Тестът го
  проверява буквално.
- **Бекъпът се следи по ВЪЗРАСТ, не по „мина ли".** Спрял крон не вдига грешка;
  липсата на файл също. Плюс подозрително малък файл — той е по-опасен от
  липсващ, защото изглежда като успех.
- **Пробата за възстановяване се планира по каданс, проверяван всеки час.**
  `setInterval` за 30 дни не преживява рестарт, а сървър, който се рестартира
  месечно, никога не би я пуснал. Резултатът се записва при ПРИКЛЮЧВАНЕ на
  задачата — „последна успешна проба" трябва да е факт, не намерение.
- **Flapping се мери по РАЗЛИКАТА в `NRestarts`.** Общият брой расте вечно и
  казва само, че услугата някога е падала. Услуга без предишна снимка не гърми.
- **Дъмпът на базата НЕ е пълен бекъп.** Записът в базата сочи към файл в том
  `uploads`, който `pg_dump` не пипа — при възстановяване получаваш цели данни и
  счупени препратки. Томовете са отделно действие. Базите се пропускат ИЗРИЧНО
  (суров tar на жива база е непоследователен) и пропускането е ВИДИМО в изхода.
- **Томът се архивира през контейнер** (`docker run -v <том>:/src:ro`), не по
  `/var/lib/docker/volumes/...` — този път е вътрешна подробност на Docker и се
  мени между драйвери.
- **Името на архива носи къс хеш от пълния път.** Нормализирането е загубено:
  `/opt/app/uploads` и `/opt/app_uploads` дават еднакъв низ и вторият архив тихо
  презаписваше първия в един и същи запуск (хванато в тест).
- **Redis изхвърля ключове ТИХО.** При `allkeys-lru` и опрян таван освобождава
  памет, като трие — няма грешка, няма ред в лога, услугата е жива. Единственият
  белег е `evicted_keys`; следи се по РАЗЛИКА. Тежестта на „пълна памет" зависи
  от политиката: с eviction е warning (работи, но губи), с `noeviction` е
  critical (записите започват да връщат грешка).
- **Статичен сайт зад Caddy иска `host` в health проверката.** Той се разпознава
  по домейн, не по порт — заявка към `127.0.0.1` без правилен Host попада в сайта
  по подразбиране и „проверката" мери чужд сайт.
- **Всяка навигация получава СВЕЖ `#view` възел** (`go()` клонира и подменя).
  Бавна секция (напр. „Ъпдейти", която чака apt) иначе се дорисува закъсняло и
  замазва секцията, към която вече си отишъл — видяно на живо: отваряш „Задачи",
  а вътре стои списъкът с пакети. Работи за всичките 32 секции наведнъж, защото
  всяка взема `view` ПРЕДИ първото `await`. **Ако пишеш нов render, вземи `view`
  в началото** — заявка след await ще хване новия възел и състезанието се връща.
- **Инлайн `var(--…)` в app.js трябва да съществува в `style.css`.** Няма
  инструмент, който да го хване: несъществуваща променлива прави текста прозрачен,
  без грешка в конзолата. Имената са `--txt`, `--txt-dim`, `--danger`, `--warn`,
  `--ok`, `--line` — не `--fg`/`--bad`/`--dim`.
- **Конфигът се пише от кода** (`saveConfig`) при 2FA и настройки за аларми —
  атомарно, mode 600, вложено сливане. Не презаписвай целия файл наивно, ще
  изгубиш тайните.
- **Аларми = промяна на състояние**, не всяка проверка. Праговите правила искат
  задържане N проверки; `sustain: false` е за стабилните (паднала услуга, изтичащ
  сертификат). Cooldown пази от спам; „възстановено“ също се известява.
- **Уеб конфигът се валидира преди reload** и се връща при провал — същият патърн
  като `autodeploy.sh`. Никога не презареждай без `nginx -t` / `caddy validate`.
- **Rollback** ползва `RELEASE_DIR` в `deploy/autodeploy.sh` (разгръща съществуващ
  release без разопаковане). Чистенето на стари releases пази текущия.

## Проверка в браузър (задължителна за промени по `public/`)
```bash
CSD_CONFIG=/tmp/dev.json node server.js &     # или npm run dev
# Playwright е глобален в средата — не се добавя към продукта (нула зависимости):
```

Внимание: `waitUntil: 'networkidle'` **никога не настъпва** — SSE потокът стои
отворен по дизайн. Ползвай `domcontentloaded`.

## Тестове
169 теста, `node --test`, без мокове на системата — тестват се само детерминистични
чисти функции: пароли/сесии, TOTP (с контролните вектори на RFC 4226), парсване на
`/proc`, рутера, allowlist-ите (unit имена, архиви, ufw правила, compose, dump),
историята, сливането на конфига, файловия запис, SLO математиката (бюджет,
burn-rate, защитата от една мигнала проба), маскирането на журнала (тайни/PII не
излизат в известие) и целия ANSI емулатор (вкл. екранирането срещу XSS).
`smoke.test.js` вдига ИСТИНСКИ сървър и минава по всички GET маршрути — той е
единственото, което хваща липсващ `import` в `routes.js` (`node --check` не го вижда).
Живите системни извиквания се проверяват ръчно на живо.
